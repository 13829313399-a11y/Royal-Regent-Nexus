### Accounts and IAM

The backend exposes account login/session behavior, registration and same-browser password-reset claim workflows, forced password change for independently flagged accounts, user management, role management, fixed system positions, effective-access calculation and permission administration. Password-reset requests have their own persisted state and notification linkage; notifications are navigation signals rather than the workflow source of truth. The public claim status and completion endpoints reveal no employee profile or review detail, and losing the original-browser Cookie requires a new application. Recovery matches usernames exactly, consistent with login and registration.

Any successful password change invalidates other pending, approved and previously timed-out claim records under the shared IAM mutation lock, preserving history/hash but clearing expiry; superseded claims cannot be reopened. Only a claim with a genuine past expiry can reopen through administrator identity verification; state reads and reopen serialize under the same lock and password mutations recheck sessions after locking. IAM changes follow the configured authorization rollout mode, apart from the narrowly scoped supplier-permission exception above. Default grants and code-owned system positions are reconciled from code rather than edited as arbitrary database records.

Registration and approval derive their allowed department codes from the same identity catalog, including warehouse and pmc-warehouse as distinct existing departments; each submission still requires an active department in its selected organization. The catalog also includes three-d-printing and functional group-management with an empty production factory. Registration remains pending until normal administrator approval; its additive request_id/submitted_at receipt does not grant a login or lookup capability. Registration and approval reject normalized phone or email reuse across other active, suspended and pending accounts inside the shared IAM database mutation lock; pending reapplications use their current request contacts. Name alone is not a unique identity. Existing duplicate accounts are not merged or removed automatically.

New registration text lengths match storage and new passwords are 6–256 characters; login and current-password verification retain the complete historical password without a new maximum. Auth errors retain a string detail with optional safe code/field_errors/retry timing/trace ID, without validation input or credentials. Private auth responses use no-store and session-cookie set/delete share configuration.

The four auth routes use persistent AuthExperienceShell with local .rr-auth styles, the existing group Logo, explicit motion controls and an immediate public boot fallback. The auth header reuses the homepage's original shared Logo SVG with identical geometry, wordmark proportions and built-in flip/sheen timing, without auth-specific Logo animation or scaling overrides. It fits a 64px desktop / 48px mobile surface with a plain light backing for contrast on the dark scene. Inline SVG preserves the shared asset while allowing auth pause/reduced-motion controls; shared branding elsewhere is unaffected. Broad soft sheen, eased layer motion and fading open-track endpoints avoid abrupt resets.

The brand scene continuously animates separate floating prism layers, facet sheen, five light tracks, orbit lights and staggered node pulses; this supersedes the reference package's two-cycle limit. Organization placement and labels remain fixed. User/background pause preserves animation time, system reduced motion renders a complete static scene, and narrow screens omit peripheral tracks/nodes. Registration uses three steps, explicit organization/department selection, guarded catalogue refresh and a real pending receipt; passwords clear on success/unmount. Account memory stores only the username/display name and all browser-storage failures are nonblocking. Recovery polling is single-flight, visible-only and disposal-safe.

Authentication generation is separate from sessionVersion: old Axios/fetch/stream authorization failures cannot invalidate a newer identity, while normal same-user refresh preserves long responses. The existing rr-identity-refresh coordinator broadcasts credential-free session-boundary signals, clears private state and reconfirms cookies in other tabs without echoing.

Restarts must preserve these values rather than inherit conflicting process settings.

The documented verified production deployment enables identity writes with `AUTHZ_MODE=enforce` and `AUTHZ_WRITES_ENABLED=true`. Production also enables scheduled changes; the local scheduling flag remains disabled.
