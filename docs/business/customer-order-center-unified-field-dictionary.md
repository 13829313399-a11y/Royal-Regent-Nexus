# 客户订单中心统一字段字典

> 文档版本：V1.4
> 文档状态：正式字段基线
> 适用模块：客户订单中心
> 更新日期：2026-07-27
> 适用范围：客户订单明细、导入预览、订单确认、客户排期输出、厂区总排期数据视图及下游供数
> 首个试点客户：BuzzBee

## 1. 文档目的

本文档确定客户订单中心第一版统一业务字段。不同客户可以继续使用不同的 PO 文件和排期格式，但进入客户订单中心后，均应转换为本文档定义的统一字段。

第一版统一字段共 17 项：

1. 来单日期；
2. P/O#；
3. Contract No.；
4. 客名/国家；
5. 产品编号；
6. 中文名称；
7. 产品名称；
8. 数量；
9. 装箱数；
10. 箱数；
11. 国家标准；
12. 单价HK；
13. 金额HK；
14. 包装；
15. 行Q；
16. 客Q；
17. 客要求走货期。

这 17 项是业务页面和标准导出的固定字段顺序。订单身份、版本、来源追溯、审核状态等系统字段必须另外保存，但不占用这 17 个业务列。

## 2. 字段设计原则

### 2.1 外部格式不统一，内部字段统一

客户原始 PO 的工作表、标签、列位和写法可以不同，由客户模板负责映射。模板解析后必须形成相同的标准字段，不允许下游模块再次解释客户原表。

### 2.2 原值与标准值同时保存

所有从客户文件读取的字段至少保留：

- 客户文件原值；
- 标准化后的字段值；
- 来源文件；
- 来源工作表；
- 来源行列或单元格；
- 使用的模板编号和版本。

### 2.3 展示字段与底层字段可以不同

“客名/国家”在页面和 Excel 中可以合并显示，但底层必须拆分保存客户、国家和市场信息，避免后期无法筛选、统计和向下游供数。

### 2.4 编号全部按文本保存

P/O#、Contract No.、产品编号和包装编号均按文本保存：

- 保留前导零；
- 保留字母、横线和版本后缀；
- 不允许 Excel 自动转成科学计数法；
- 不因纯数字外观而转换为整数。

### 2.5 派生值统一计算

箱数和金额HK由标准字段计算，不以客户 Excel 中已有公式作为权威值。系统应同时保留计算规则和计算结果。

| 1 | 来单日期 | `order_received_date` | `DATE` | 必填 | 公司实际收到该 PO 的业务日期 |
| 2 | P/O# | `customer_po_no` | `STRING` | 条件必填 | 客户 PO 编号；客户格式不提供时可空 |
| 3 | Contract No. | `sales_contract_no` | `STRING` | 必填 | 销售合同号 |
| 4 | 客名/国家 | `customer_country_display` | 展示字段 | 必填 | 由客户、国家或市场字段组合显示 |
| 5 | 产品编号 | `product_no` | `STRING` | 必填 | 模板提取并经产品映射确认的统一显示编号 |
| 6 | 中文名称 | `product_name_zh` | `STRING` | 原则必填 | 产品映射主数据或人工确认 |
| 7 | 产品名称 | `product_name_en` | `STRING` | 必填 | 客户 PO 中的产品名称，BuzzBee 默认英文名称 |
| 8 | 数量 | `order_quantity` | `DECIMAL(18,3)` | 必填且大于 0 | 客户要求数量 |
| 9 | 装箱数 | `units_per_carton` | `DECIMAL(18,3)` | 必填且大于 0 | 每箱装多少产品 |

| 15 | 行Q | `line_q_date` | `DATE` | 可空 | 行Q业务日期，具体业务含义待最终确认 |
| 16 | 客Q | `customer_q_requirement` | `TEXT` | 可空 | 客户验货日期或完整验货要求 |
| 17 | 客要求走货期 | `customer_requested_ship_date` | `DATE` | 必填 | 客户要求的走货日期 |

## 4. 字段详细定义

### 4.1 来单日期

| 项目 | 定义 |
| --- | --- |
| 业务名称 | 来单日期 |
| 技术字段 | `order_received_date` |
| 含义 | 公司或跟客实际收到客户 PO 的日期 |
| 类型 | 日期 |
| 是否必填 | 是 |
| 显示格式 | `YYYY-MM-DD` |
| 取值原则 | 优先由上传人确认；如系统自动带入当天日期，用户在确认前可修正 |

“来单日期”不是：

- 客户 PO 文件中的制单日期；
- 用户上传文件的技术时间戳；
- 客要求走货期；
- 行Q或客Q日期。

旧 BuzzBee 程序把执行写入当天作为来单日期。新系统应保存真实业务来单日期，不能在重新导入或重新导出时被当天日期覆盖。

### 4.2 P/O#

| 项目 | 定义 |
| --- | --- |
| 业务名称 | P/O# |
| 技术字段 | `customer_po_no` |
| 含义 | 客户提供的 Purchase Order 编号 |
| 类型 | 文本 |
| 是否必填 | 按客户模板决定；WMU/WMC 必填 |
| 唯一性 | 不能单独作为全系统唯一键 |

规则：

- 保留前导零；
- 保留字母、横线和其他有效字符；
- 去除首尾空格；
- 不擅自改变大小写；
- 同一 P/O# 可以包含多条产品或多个走货批次；
- 标签式 BuzzBee 合同若确实未提供 P/O# 时允许为空，但必须有 Contract No.；真实 AAFES 样本已证明 P/O# 也可能位于右侧唛头区。

### 4.3 Contract No.

| 项目 | 定义 |
| --- | --- |
| 业务名称 | Contract No. |
| 技术字段 | `sales_contract_no` |
| 含义 | 公司与客户业务往来使用的销售合同编号 |
| 类型 | 文本 |
| 是否必填 | 是 |

规则：

- 按文本保存；
- 纯数字编号不保留由 Excel 产生的无意义 `.0`；
- 保留原始编号文本用于追溯；
- 一个合同可包含多条订单明细；
- Contract No. 不能与 P/O# 混为同一个字段。

### 4.4 客名/国家

“客名/国家”是一个业务展示字段，底层必须拆分。

| 底层字段 | 含义 | 是否必填 |
| --- | --- | --- |
| `customer_id` | 系统客户主档编号 | 是 |
| `customer_name` | 客户正式名称 | 是 |
| `country_code` | 国家或地区代码 | 按客户业务需要 |
| `country_name` | 国家或地区名称 | 按客户业务需要 |
| `market_code` | 市场或渠道代码，例如 WMU、WMC | 条件必填 |
| `source_customer_text` | 客户文件中识别到的原始文字 | 有来源时保存 |

推荐显示规则：

```text
有国家/市场：客户简称 / 国家或市场
无国家/市场：客户简称
```

BuzzBee 的旧工作簿会直接显示 `WMU`、`WMC` 等文字。迁移后应区分：

- 客户主档：BuzzBee；
- 市场代码：WMU 或 WMC；
- 国家标准：美国标准或加拿大标准。

不得把 WMU/WMC 直接当作客户主档名称。

### 4.5 产品编号

| 项目 | 定义 |
| --- | --- |
| 业务名称 | 产品编号 |
| 技术字段 | `product_no` |
| 含义 | 订单页面和标准导出使用的统一产品编号 |
| 类型 | 文本 |
| 是否必填 | 是 |

底层建议同时保存：

| 字段 | 含义 |
| --- | --- |
| `source_product_no` | 客户文件中的原始编号 |
| `customer_item_no` | 客户货号 |
| `factory_item_no` | 公司内部产品编号 |
| `product_no` | 当前统一业务展示编号 |
| `product_mapping_id` | 使用的产品映射记录 |

BuzzBee 当前 `Our Item#` 或首页 `E14` 读取到的编号应先作为客户来源编号保存。是否直接作为统一产品编号，应由 BuzzBee 产品映射主数据确认。

匹配失败时不得静默生成新产品，也不得默认归类为子弹枪。

### 4.6 中文名称

| 项目 | 定义 |
| --- | --- |
| 业务名称 | 中文名称 |
| 技术字段 | `product_name_zh` |
| 含义 | 公司内部统一使用的中文产品名称 |
| 类型 | 文本 |
| 来源 | 产品映射主数据或跟客人工确认 |

规则：

- 同一有效产品编号原则上只有一个当前中文名称；
- 客户原文件没有中文名称时，可以根据产品映射补充；
- 自动映射结果必须记录映射版本；
- 同一编号匹配多个名称时形成异常；
- 人工修改不得反向覆盖产品主数据，除非经过主数据维护流程。

### 4.7 产品名称

| 项目 | 定义 |
| --- | --- |
| 业务名称 | 产品名称 |
| 技术字段 | `product_name_en` |
| 含义 | 客户 PO 中的产品名称；BuzzBee 当前主要为英文名称 |
| 类型 | 文本 |
| 是否必填 | 是 |

规则：

- 优先保留客户原文；
- 不自动翻译后覆盖原文；
- 可另外保存标准产品英文名；
- 客户名称与产品主数据名称不一致时提示，但不应自动丢失客户原文。

### 4.8 数量

| 项目 | 定义 |
| --- | --- |
| 业务名称 | 数量 |
| 技术字段 | `order_quantity` |
| 含义 | 本订单明细、本交付需求的客户要求数量 |
| 类型 | `DECIMAL(18,3)` |
| 是否必填 | 是 |
| 校验 | 必须大于 0 |

底层还应保存 `quantity_unit`。BuzzBee 默认单位为 `PCS`，且当前试点数量应为正整数。

禁止：

- 使用浮点数计算金额；
- 将空值当作 0；
- 将负数变更直接写入当前有效订单；
- 把库存、样板或备料数量混入订单数量。

### 4.9 装箱数

| 项目 | 定义 |
| --- | --- |
| 业务名称 | 装箱数 |
| 技术字段 | `units_per_carton` |
| 含义 | 每个出口箱装多少件产品 |
| 类型 | `DECIMAL(18,3)` |
| 是否必填 | 是 |
| 校验 | 必须大于 0 |

BuzzBee 旧 WMU/WMC 程序在装箱数为空时默认填 `4`。统一字段不允许使用该固定默认值。

可从已审核产品主数据带出建议值，但必须：

- 标明“来自主数据建议”；
- 与客户 PO 不一致时形成异常；
- 经跟客确认后才能成为当前订单值。

### 4.10 箱数

| 项目 | 定义 |
| --- | --- |
| 业务名称 | 箱数 |
| 技术字段 | `carton_count` |
| 含义 | 根据订单数量和装箱数计算的箱数 |
| 类型 | `DECIMAL(18,3)` |
| 计算 | `订单数量 ÷ 装箱数` |

计算规则：

```text
carton_count = order_quantity / units_per_carton
```

处理原则：

- 能整除时显示整数箱数；
- 不能整除时显示精确结果并产生“非整箱”警告；
- 客户订单中心不得静默向上取整后改变客户数量口径；
- 实际尾箱、装柜和出货箱数由 PMC/仓库或走货模块处理；
- 如业务确认必须整箱，非整除应作为阻断性错误。

### 4.11 国家标准

| 项目 | 定义 |
| --- | --- |
| 业务名称 | 国家标准 |
| 技术字段 | `compliance_standard` |
| 含义 | 订单产品需满足的国家、地区或市场标准 |
| 类型 | 枚举代码 |
| 是否必填 | 是 |

第一版建议值：

| 标准代码 | 显示名称 |
| --- | --- |
| `US` | 美国标准 |
| `CA` | 加拿大标准 |
| `EU` | 欧洲标准 |
| `AU` | 澳洲标准 |
| `CN` | 国标 |
| `OTHER` | 其他，必须填写说明 |

规则：

- 客户文件明确给出的标准优先；
- 市场代码可用于提供建议值；
- 关键词识别只能作为建议，不能静默确认；
- `WMU` 建议美国标准，`WMC` 建议加拿大标准；
- 标准与国家/市场冲突时必须提示。

### 4.12 单价HK

| 项目 | 定义 |
| --- | --- |
| 业务名称 | 单价HK |
| 技术字段 | `unit_price_hkd` |
| 含义 | 本订单明细的港币单位价格 |
| 类型 | `DECIMAL(18,6)` |
| 币种 | 固定为 HKD |
| 是否必填 | 由客户模板和业务流程决定 |

规则：

- 使用十进制定点数保存；
- 录入算术表达式时，同时保存表达式原文和计算结果；
- 同一货号历史价格只能作为提示，不能自动覆盖本订单价格；
- 价格变更应随 PO 版本保留历史；
- 价格为空时，金额HK为空，不得按 0 处理。
- BuzzBee 基础试用允许跟客在预览页明确勾选“跳过并后补”；导出排期中的单价及金额单元格保持空白，不写入 `0` 或虚构价格。
- 人工跳过只解除本次文件导出的阻断，不代表价格已经确认；未来订单台账必须保留跳过人、跳过时间、原因和后补状态。

### 4.13 金额HK

| 项目 | 定义 |
| --- | --- |
| 业务名称 | 金额HK |
| 技术字段 | `amount_hkd` |
| 含义 | 本订单明细的港币金额 |
| 类型 | `DECIMAL(20,4)` |
| 计算 | `数量 × 单价HK` |

计算规则：

```text
amount_hkd = order_quantity × unit_price_hkd
```

规则：

- 由系统统一计算；
- 原始精度至少保留 4 位小数；
- 页面和 Excel 的显示小数位可配置；
- 汇总必须使用未提前舍入的明细结果；
- 单价为空时金额为空；
- 不使用客户 Excel 的现成金额公式作为权威结果。

### 4.14 包装

| 项目 | 定义 |
| --- | --- |
| 业务名称 | 包装 |
| 技术字段 | `packaging_requirement` |
| 含义 | 客户要求使用的包装编号和完整包装说明 |
| 类型 | 文本 |
| 是否必填 | 按客户和产品决定 |

底层建议拆分：

| 字段 | 含义 |
| --- | --- |
| `packaging_reference_no` | 结构化包装编号 |
| `packaging_requirement_raw` | 客户文件中的原始包装全文 |
| `packaging_requirement_note` | 编号以外的备注、版本和特殊要求 |

BuzzBee 示例可能包含：

- `11760-11-25-EN`；
- `40190-05-25-EN8`；
- `54234-11-23-EN(r1)`；
- 包装编号加 PDQ、颜色或版本说明。

统一显示字段应优先显示完整有效包装要求，不能只保留正则识别到的编号主体。

### 4.15 行Q

| 项目 | 定义 |
| --- | --- |
| 业务名称 | 行Q |
| 建议技术字段 | `line_q_date` |
| 当前观察 | BuzzBee 旧评审表中通常为日期 |
| 建议类型 | 日期 |
| 是否必填 | 暂定可空 |

BuzzBee 旧程序当前写入方式：

- 有 `Inspection Date` 时写验货日期；
- 没有时回填客要求走货期。

该回填方式会混淆验货日期与走货日期，新系统不应直接沿用。正式开发前需确认“行Q”的完整中文业务含义、责任部门和日期口径。

在含义未确认前：

- 保留原值；
- 仅明确日期时才转换为 `line_q_date`；
- 不允许用走货期静默补齐；
- 不将其作为生产排产日期。

### 4.16 客Q

| 项目 | 定义 |
| --- | --- |
| 业务名称 | 客Q |
| 建议技术字段 | `customer_q_requirement` |
| 当前观察 | 既可能是日期，也可能是“验货+抽板”等完整文字要求 |
| 建议类型 | 文本 |
| 是否必填 | 暂定可空 |

BuzzBee 实际数据示例包括：

- 单一验货日期；
- `2026/4/20验货+抽12板`；
- 其他客户验货安排。

因此“客Q”不能只设计为日期字段。建议同时派生：

| 字段 | 含义 |
| --- | --- |
| `customer_q_requirement` | 客户要求原文 |
| `customer_q_date` | 能明确提取时的客户验货日期 |
| `customer_q_note` | 抽板数量或其他验货说明 |

BuzzBee 旧程序把同一个 `Inspection Date` 同时写入“行Q”和“客Q”，无法完整表达上述差异。新模板应支持分别映射。

### 4.17 客要求走货期

| 项目 | 定义 |
| --- | --- |
| 业务名称 | 客要求走货期 |
| 技术字段 | `customer_requested_ship_date` |
| 含义 | 客户要求公司完成走货或交付动作的日期 |
| 类型 | 日期 |
| 是否必填 | 是 |
| 显示格式 | `YYYY-MM-DD` |

规则：

- 保存客户原值和标准日期；
- 不与公司承诺交期、实际走货日期混用；
- 不因下游排产调整而修改客户要求原值；
- 客户变更该日期时生成新的 PO 版本；
- 不同客户的“走货期”可能代表出厂、交仓、装船或其他节点，必须由客户模板说明。

## 5. BuzzBee 来源映射

## 9. 厂区总排期数据投影

### 9.1 正式定义

客户订单中心的“厂区总排期”不是另一张 Excel，也不是把各客户排期合并后导出一个新文件。

它是客户订单中心内部的一张**订单交付排期数据视图**：

- 以17个统一字段和订单系统标识为基础；
- 只投影当前厂区需要关注的有效订单和交付需求；
- 按客户、走货月份、走货周和客要求走货期组织；
- 计算临期、逾期等交付风险；
- 供PMC及生产模块读取已确认需求；
- 汇总下游模块回传的生产状态；
- 在客户订单中心只读显示生产未完成和异常。

因此：

- 流程01可以继续按客户格式输出客户排期 Excel；
- 厂区总排期本身以系统数据和页面为准；
- 本阶段不要求导出“厂区总排期 Excel”；
- 不需要再导入另一张总排期工作簿进行合并。

### 9.2 与订单数据台账的区别

| 对象 | 订单数据台账 | 厂区总排期 |
| --- | --- | --- |
| 主要用途 | 保存全部订单主数据、来源、版本和确认状态 | 查看厂区未来各月需要走货的PO和交付风险 |
| 数据范围 | 包括历史版本、待确认、阻断、已关闭订单 | 默认只展示当前有效交付需求，可单独筛选待确认异常 |
| 组织方式 | 按订单、PO、合同、产品查询 | 按厂区、客户、月份、周次、走货日期组织 |
| 权威内容 | 客户订单原值和订单版本 | 从订单台账派生的交付视图 |
| 生产状态 | 只保存关联标识 | 只读汇总生产模块反馈 |
| 是否可修改生产数据 | 否 | 否 |
| 是否为Excel | 否 | 否 |

厂区总排期不能复制一份订单数据形成第二套主数据。它必须通过 `order_line_id`、`delivery_demand_id` 和订单版本实时关联订单数据台账。

### 9.3 排期派生字段

以下字段不改变17个基础字段的定义，而是系统根据订单和日期派生：

| 字段代码 | 中文名称 | 规则/用途 |
| --- | --- | --- |
| `factory_id` | 所属厂区 | 确定订单需求供哪个厂区使用 |
| `schedule_month` | 走货月份 | 从客要求走货期派生，格式 `YYYY-MM` |
| `schedule_week` | 走货周 | 从客要求走货期派生，用于周视图 |
| `days_to_ship` | 距走货天数 | 客要求走货期减当前业务日期 |
| `delivery_risk_status` | 交付风险状态 | 计划中、即将到期、临期、逾期、已走货 |
| `order_data_status` | 订单数据状态 | 待确认、阻断、已确认、已变更、已取消、已关闭 |
| `publishable_to_downstream` | 可供下游读取 | 只有当前有效且已确认版本为是 |
| `demand_version` | 需求版本 | 下游必须记录所使用的订单/交付需求版本 |
| `last_order_change_at` | 最近订单变更时间 | 用于提醒下游是否使用旧版本 |

临期阈值不能硬编码在客户模板中，应作为公司级可配置规则。建议先提供：

- 30天内：即将到期；
- 7天内：临期；
- 已过客要求走货期且未关闭：逾期。

正式天数由业务确认后配置。

详细优先级、去重和解除规则见《[客户订单中心异常与提醒规则](./customer-order-center-exception-reminder-rules.md)》。

### 9.4 生产反馈只读字段

下游生产模块完成后，按订单行/交付需求版本回传以下摘要：

| 字段代码 | 中文名称 | 权威来源 |
| --- | --- | --- |
| `production_overall_status` | 生产总体状态 | PMC或生产任务聚合规则 |
| `production_completion_rate` | 生产完成率 | 各生产模块已完成数量聚合 |
| `production_completed_qty` | 已完成数量 | 生产模块 |
| `production_incomplete_qty` | 未完成数量 | 需求数量减已完成数量 |
| `production_blocking_department` | 当前阻断部门 | 啤机、喷油、装配等生产模块 |
| `production_incomplete_reason` | 未完成原因 | 对应生产模块 |
| `production_feedback_at` | 最后反馈时间 | 对应生产模块 |
| `production_source_record_id` | 下游记录ID | 用于跳转和追溯 |

处理原则：

- 客户订单中心只能读取和展示这些字段；
- 跟客人员不能在客户订单中心修改生产完成数量；
- 各生产模块仍负责本部门排产和执行；
- 同一个订单有多个生产环节时，需要明确总体状态的聚合规则；
- 生产反馈必须带 `order_line_id`、`delivery_demand_id` 和 `demand_version`；
- 下游使用旧订单版本时，客户订单中心显示“版本落后”提醒。

### 9.5 厂区总排期页面指标

页面至少支持：

- 按厂区、客户、走货月份、走货周筛选；
- 本月待走货PO数；
- 本月待走货产品行数和总数量；
- 未来30天到期订单；
- 未来7天临期订单；
- 已逾期未关闭订单；
- 生产未完成订单；
- 因订单字段待确认而尚未供下游读取的订单；
- 按客户汇总当月PO和数量；
- 打开订单查看17字段、来源和生产反馈。

### 9.6 下游供数原则

详细数据合同见《[客户订单中心下游数据接口清单](./customer-order-center-downstream-data-interface.md)》。

生产部门调用厂区总排期数据时：

- 默认只返回当前有效、已确认、可发布的订单版本；
- 返回稳定ID和版本号，不依赖Excel行号；
- 客户订单变更产生新版本，不原地覆盖；
- 生产模块不得反向修改17个订单基础字段；
- 单价HK和金额HK属于敏感商业字段，生产接口默认不返回，除非岗位权限明确授权；
- 生产反馈通过独立状态接口或事件回传，不写入客户订单主表。

## 10. 统一校验规则

### 10.1 阻止确认

- 来单日期为空或无效；
- Contract No. 为空；
- 产品编号为空；
- 产品名称为空；
- 数量为空、非数字或小于等于 0；
- 装箱数为空、非数字或小于等于 0；
- 国家标准无法确认；
- 客要求走货期为空或无效；
- WMU/WMC 缺少 P/O#；
- 金额HK与系统计算结果不一致；
- 同一订单行疑似重复但尚未处理。

### 10.2 警告并要求跟客确认

- 普通合同没有 P/O#；
- 中文名称未匹配；
- 产品编号只有客户编号，未映射工厂编号；
- 数量不能被装箱数整除；
- 单价HK为空；
- 包装要求为空或只识别到部分编号；
- 行Q为空；
- 客Q为空；
- 行Q晚于客要求走货期；
- 客Q日期晚于客要求走货期；
- 客名、国家标准和市场代码相互冲突。

## 11. 版本与变更规则

以下字段发生变化时，应视为可能影响下游的 PO 变更：

- P/O#；
- Contract No.；
- 客户或国家/市场；
- 产品编号；
- 数量；
- 装箱数；
- 国家标准；
- 包装；
- 行Q；
- 客Q；
- 客要求走货期。

价格类字段变更是否需要同步 PMC，由业务流程决定，但必须保留版本和审计记录。

变更原则：

- 已确认数据不可原地覆盖；
- 新变更生成新版本；
- 系统展示新旧字段差异；
- 跟客确认后再发布；
- 下游接收记录必须带版本号；
- 原始来单日期通常保留，另记录变更文件接收日期。

## 12. 待确认事项

以下事项不影响建立字段基线，但必须在 BuzzBee 试点开发前确认：

1. “行Q”的完整中文名称、责任岗位及准确日期定义；
2. “客Q”是否统一指客户验货要求，以及是否需要固定拆分“日期、抽板数量、备注”；
3. 产品编号的统一展示值默认使用客户货号还是工厂货号；
4. 中文名称缺失是否阻止订单发布；
5. 普通合同未提供 P/O# 时是否允许直接发布；
6. 单价HK是否为所有客户的确认必填项；
7. 非整箱订单是否允许发布；
8. 客要求走货期对 BuzzBee 分别代表出厂日、交仓日还是其他节点；
9. 美国单2%折扣的适用客户、市场、生效日期和计算规则；
10. `利宝贴纸`、`日期码`是否需要成为 BuzzBee 客户扩展字段。
11. 公司级“即将到期”和“临期”分别提前多少天；
12. 多个生产部门反馈时，生产总体完成率和阻断部门如何聚合；
13. 哪些生产岗位可以查看单价HK和金额HK；
14. 订单达到什么条件后从厂区总排期的活动视图移入历史。

## 13. 验收标准

统一字段字典落地时至少满足：

- 所有客户模板均映射到相同的 17 项业务字段；
- 17 项字段在页面、导出和下游接口中的含义一致；
- P/O#、Contract No.、产品编号保留前导零和原始格式；
- 客名/国家在底层可以分别查询和统计；
- 箱数、金额HK由系统统一计算；
- 行Q、客Q不再被同一个日期无差别覆盖；
- 客Q可以保留完整验货文字要求；
- 客要求走货期与公司承诺、生产排期和实际走货日期分离；
- 厂区总排期能按客户和月份展示待走货PO；
- 临期、逾期和生产未完成状态来源明确；
- 只有有效已确认版本可供生产部门读取；
- 生产反馈在客户订单中心只读展示；
- 厂区总排期不依赖另一张Excel，也不要求输出总排期Excel；
- 所有解析字段都能追溯到原始文件；
- 已确认字段变更生成新版本；
- 库存、备料、生产排产和实际走货不在本字典中维护；
- 客户特殊字段通过扩展字段处理，不改变统一字段含义。

---

**字段基线决定：**

本文档定义的 17 个业务字段是客户订单中心第一版统一订单明细列。BuzzBee 作为首个试点客户，应先完成这 17 项字段的真实样本映射和确认，再建立其他客户模板。后续新增客户时，优先复用本字典；客户独有信息使用扩展字段，不轻易增加或改变统一字段。
