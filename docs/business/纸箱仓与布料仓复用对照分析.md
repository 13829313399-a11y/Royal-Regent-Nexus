# 纸箱仓与布料仓功能对照及复用分析

- 分析日期：2026-10-22
- 分析范围：`纸箱采购协同` 中的仓库作业（收料、库存、盘点、月结、异常、日志）与华康 C `布料仓`（`src/features/warehouse-operations/`），不含纸箱客户报价、箱唛资料库、供应商门户等外围模块。
- 结论口径：代码与当前页面文案一致；文档只描述“现在能做什么”和“复制过去需要改什么”，不代表已排期或已获业务批准。

## 一、结论摘要

1. **没有整页可以直接复制。** 两仓的页面外壳、表格密度和操作习惯已经同源，但库存身份不同：纸箱按“客户 + 合同 + 货号 + 纸品 + 纸质 + 规格 + 单位”识别，并按币种计价；布料按“物料 + 批次 + 缸号 + 卷号 + 仓位 + 原单位”识别，价格只作参考。直接复制数据表或接口会把两种库存混成一套。
2. **真正可复制的是机制和交互。** 期初整批撤销、盘点复核、月结锁账、异常工单、打印、服务端日志分页、异步导出，属于“流程可搬、字段要换”；手机端单据、扫码定位、配套发料、单位主数据，则反向可搬。
3. **纸箱 → 布料的主要缺口是“金额与期间”**：布料仓已实现收发数量、期初、盘点、月度和订单汇总，但计价、正式锁月、应付/供应商对账、异常工单、单据打印仍未实现。纸箱在这些方面最成熟，但也最依赖客户/币种/应付口径，不能照搬。
4. **布料 → 纸箱的主要缺口是“现场作业”**：布料仓有手机全屏单据、扫码定位、同订单配套发料、单位/物料主数据；纸箱的表格已能随容器宽度变形，但缺少面向仓库现场的触屏单据和扫码入口。
5. **不建议为了复用而合并两套库存账。** 两仓应继续各自持有库存、权限和审计；共享的只应是页面壳、通用交互和少量无业务依赖的工具。

## 二、两仓当前边界

| 维度 | 纸箱仓 | 布料仓 |
| --- | --- | --- |
| 业务定位 | 纸箱采购协同中的仓库段：订单下达后收料、分仓、领用、盘点、客户月结 | 华康 C 布料/辅料仓：接收采购已下达资料，办理实收、领料、退料、调仓、期初、盘点、数量对账 |
| 厂区 | 多厂区（按 `factory_id`） | 当前固定 `huakang-c`（`WAREHOUSE_FACTORY`、`services/warehouse_operations.py` 的 `FACTORY`） |
| 权限族 | `carton_procurement:*`，PMC/仓库范围 | `fabric_operations:read/operate/quality/correct`；资料写入走 `fabric_warehouse:import` |
| 库存身份 | 客户、合同、货号、纸品、纸质、规格、单位（币种用于计价） | 物料、批次、缸号/卷号、仓位、原单位 |
| 上游来源 | 纸箱订单、供应商门户、送货单导入 | 金蝶物料跟踪表导入、供应商/车间交接单扫码、手工凭证 |
| 金额 | 单价、币种、移动加权计价、期末金额、应付 | 单价/币种仅作原单参考，不计金额、不生成应付 |
| 期间 | 月结草稿 → 核对 → 锁定；锁定后禁止补记或冲销影响该月结存 | 月度数量汇总，明确“未关账” |
| 现场 | 桌面为主，表格容器查询自适应；无扫码 | 手机全屏单据、44px 触控、扫码定位、配套发料 |

## 四、纸箱 → 布料：可复制清单

分级：**A 直接复用**（改字段/常量即可）；**B 适配复用**（流程可用，换数据源与校验）；**C 仅借鉴**（重写实现）；**D 不复制**。

### 1. 期初导入“整批撤销”（B，约 1–2 人日）

**布料现状**：期初可下载模板、预览、确认入账（`fabric_inventory_setup.py` 的 `apply_opening`），但入账后没有撤销入口；导错只能另建盘点或走后续业务处理，操作成本高。

**纸箱实现**：`carton_opening_batches.py` 提供批次列表、撤销预览、整批撤销；`CartonOpeningInventoryBatches.vue` 有“预览整批撤销 → 核对明细 → 填写原因 → 确认”的完整交互。撤销按原导入批次抵消全部期初流水，原记录保留；已锁账、已有后续收发/调仓、正在盘点、已逐笔冲销时整批拒绝。

**复制方式**：
- 复用 `list_batches` / `preview_batch_reversal` / `reverse_batch` 的“预览指纹 + 原子撤销 + 依赖检查”结构。
- 布料的数据源是 `warehouse_operations_documents` 中的 `OPENING_IMPORT` 事件，不是纸箱的 `CartonInventoryMovement`；撤销应追加一条反向 `OPENING` 事件（现有 `CORRECTION` 只接受实收/出库/退料/调仓/加工发出/包装发出，需扩展或新增 `OPENING_REVERSAL`），而不是删除原导入。
- 依赖检查改为：该期初批次是否已被盘点引用、是否有后续收发/调仓、是否落在已锁月份、是否已整批撤销。
- 前端可直接照 `CartonOpeningInventoryBatches.vue` 的布局改字段（物料、缸号、卷号、仓位、原单位）。

**风险**：布料期初没有金额，撤销不涉及计价；但必须确认“整批撤销”不会让采购待收或供应商本月进货数量回退——布料期初本来就不计入采购实收，这一点比纸箱简单。

### 2. 盘点独立复核（B，约 1–2 人日）

**布料现状**：`fabric_inventory_setup.py` 的 `act_count` 允许有 `correct` 权限的人直接 `POST` 入账；没有“提交待复核”状态，也没有“创建人不能自己复核”的限制。

**纸箱实现**：`carton_stocktake.py` 的 `act_stocktake` 支持 `SUBMIT` / `APPROVE` / `RETURN` / `CONFIRM`；`APPROVE` 明确拒绝创建人或提交人本人，必须另一位主管复核。`CartonStocktakeWorkspace.vue` 有对应的复核按钮与原因输入。

**复制方式**：
- 给布料盘点单增加 `SUBMITTED` 状态和 `submitted_by/at`、`reviewed_by/at` 字段（可复用现有 `warehouse_operations_documents` 的 payload，不必新建表）。
- `POST` 前增加“提交人 ≠ 复核人”校验；保留现有 `correct` 权限作为复核权限，不新增角色。
- 复核退回时保留草稿和差异原因，不重新生成快照。

**注意**：纸箱本身也允许有权限者直接确认（`CONFIRM`），所以复制的是“可选的独立复核”，不是强制双人。是否强制由布料业务决定。

### 3. 期间锁账（C，约 3–5 人日）

**布料现状**：月度数量汇总明确“未关账”“未确认或锁定月份”（`FabricMonthlyWorkspace.vue`、`WarehousePage.vue` 月结记录页）。所有日常收发都只看业务日期，没有“已锁月份禁止补记”的校验。

**纸箱实现**：`CartonClosing` 模型按“厂区 + 期间 + 客户 + 币种”保存期初、入库、出库、调整、期末、期末金额和状态；`carton_procurement.py` 的 `_ensure_period_open` 在所有库存写入前检查该客户是否存在更晚的 `LOCKED` 期间；界面提供生成草稿、核对确认、主管锁账、填写原因解锁。

**复制方式**：
- 借状态机（DRAFT → PENDING → CONFIRMED → LOCKED + 解锁留痕）和“写入前检查期间”的位置，不复制客户/币种/金额字段。
- 布料按“仓库（fabric/semi）+ 月份”建锁，数量口径即可；期初、盘点、冲销、调仓都要纳入同一检查。
- 锁账前必须处理未核价、未核实仓位、未完成盘点等阻断项；布料目前没有计价，阻断项可先限定为“盘点草稿、期初未核对、未冲销单据”。

**风险**：这是跨模块的状态约束，必须同时覆盖采购实收、日常收发、期初、盘点、冲销五条写入路径；漏一条就会出现“锁了还能记”的漏洞。需要独立测试与迁移评审。

### 4. 异常工单（B，约 3–4 人日）

**布料现状**：异常处理只有“单据更正”和“受限库存”；页面说明明确“短收、超收、责任分派与处理关闭的独立异常流程尚未接入”。

**纸箱实现**：`CartonException` 模型含来源类型/ID、分类、严重度、客户/合同/货号、责任部门、状态、处理说明、解决人/时间；接口支持列表筛选、单条更新、批量推进；界面有勾选、批量处理、处理说明和统计卡片。

**复制方式**：
- 复制“来源单据 + 类型 + 责任部门 + 状态机（OPEN/IN_PROGRESS/RESOLVED/CLOSED）+ 处理留痕”的模型，字段换成布料维度（物料、供应商、领用方、批次、仓位）。
- 先接两类真实来源：收料短收/超收、领料差异；不要一开始做通用工单平台。
- 与现有冲销、盘点差异分开：异常工单只做跟踪和闭环，不直接改库存。

### 5. 送货单打印（A，约 0.5–1 人日）

**布料现状**：有 `HandoverOriginalPrint.vue`（把供应商原单加二维码后打印）和交接单页面打印，但没有仓库自己生成的收料单/送货单打印。

**纸箱实现**：`deliveryNotePrint.ts` 是一个纯函数，输入单据和抬头，输出 A4 HTML；`CartonSupplierView.vue` 用新窗口打印。字段包括客户、订单/纸品、规格、数量、单位、合计、签章栏。注意纸箱的仓库视图本身没有打印入口，这个能力只在供应商门户使用；采购单 Excel 是另一套导出，不可混用。

**复制方式**：
- 直接复制这个纯函数和打印调用方式，把列换成布料字段：供应商、送货单号、物料编码/名称、缸号、卷号、原单位、实收数量、仓位、备注。
- 与现有二维码打印结合：打印页顶部保留二维码，扫码仍回到交接单，不改变库存。

**注意**：打印内容只是凭证，不写入任何业务状态；不要因为打印而生成收料或推进采购进度。

### 6. 服务端操作日志（B，约 2–3 人日）

**布料现状**：`FabricActivityLog.vue` 通过 `workspace('fabric')` 全量取回文档后在浏览器筛选、分页（50 条/页），没有服务端查询和导出。数据量增大后会变慢。

**纸箱实现**：`GET /carton-procurement/audit-events` 支持关键字、事件类型、操作人、日期范围、排序、分页和 `summary_only`；页面只取当前页。

**复制方式**：
- 在布料现有投影上增加一个只读查询接口，按操作时间/业务日期/类型/经办人/状态过滤，服务端分页。
- 事件来源仍是 `warehouse_operations_documents`，不新增第二套日志。
- 不复制纸箱的 `CartonAuditEvent` 表；布料已经有统一文档账本，缺的只是查询层。

### 7. 异步导出任务（C，约 1–2 人日，按需）

**布料现状**：月度导出是同步生成 xlsx；数据量大时可能超时。

**纸箱实现**：`carton_file_jobs.py` 提供有界任务槽、超时、结果文件短时保存、按用户隔离下载。只在确有大数据量时复制；否则保持同步更简单。

### 8. 不建议复制：计价/核价/应付/供应商对账（D）

纸箱的 `carton_inventory_valuation.py`、`CartonPriceReviews.vue`、`CartonPayables.vue`、`carton_monthly_settlement.py` 都建立在“客户 + 币种 + 采购应付”上。布料仓当前定位是数量仓，价格只作原单参考；直接复制会把采购应付职责带进仓库，和现有“采购负责下单、仓库只收发”的边界冲突。另需注意：纸箱的供应商月度对账后端流程（提交/确认/异议/锁账）已存在，但当前页面明确标注“只读对账，不提交、不锁定”，对账导出也没有接线；它不是一套可以直接照搬的完整前端能力。若业务确需布料计价，应单独设计“物料 + 单位 + 期间”的估值口径，而不是改纸箱字段。

## 五、布料 → 纸箱：可复制清单

### 1. 手机端全屏单据（B，约 3–5 人日）

**布料实现**：`fabric-mobile.css` 在 ≤700px 时把弹窗变为全屏，输入 44px、字号 16px、底部安全区、表格变卡片；`FabricReceiptDialog.vue`、`WarehouseBulkIssueDialog.vue`、`FabricIssueGroupDialog.vue` 都复用同一套表单状态和提交处理。

**纸箱现状**：`layout.css` 用容器查询把表格变成带标签的字段（900px/600px），但弹窗仍是桌面尺寸，没有触屏尺寸和安全区处理。

**复制方式**：
- 不复制具体类名，复制规则：全屏 dialog、44px 控件、16px 输入、底部安全区、表格转单列卡片、提交区固定可见。
- 先改收料和批量出库两个高频弹窗，不改整页。
- 复用现有表单状态与提交函数，只改样式和布局，避免出现第二套业务逻辑。

### 2. 扫码定位单据（B，约 5–8 人日，依赖二维码打印）

**布料实现**：`material-handover` 模块的扫码页通过二维码定位交接单；扫码本身不记账，只打开单据，仓库核对实物后再收料/发料。

**纸箱现状**：没有扫码入口（`CartonProcurementView.vue` 无“扫码/二维码”相关实现）。

**复制方式**：
- 先在送货单打印页加二维码（可复用纸箱 `deliveryNotePrint.ts` 的打印流程），二维码内容只放单据号/校验串。
- 扫码页可参考 `MaterialHandoverView.vue` 的“扫码 → 查单 → 打开收料”流程，但数据源换成纸箱送货单/收料单。
- 扫码只做定位，不自动确认收料；重复扫码不重复记账。

**风险**：纸箱供应商门户已有自己的单据体系，扫码会多一个入口，需要确认由供应商打印还是仓库打印，以及旧单没有二维码时的手工兜底。

### 3. 同订单配套发料（C，约 3–5 人日，先做业务确认）

**布料实现**：`fabric_issue_groups.py` 把同一订单/生产单的 2–100 个领料申请组成配套组，按缸号复用、最早批次、按比例拆分生成发料计划，整组原子过账；不合并原申请。

**纸箱现状**：有勾选库存批量出库，但出库对象是库存行，不是“同一订单的多纸品申请”。

**复制方式**：
- 如果纸箱车间确实按订单成套领用多种纸品，可复制“组 + 计划 + 原子过账”的结构；否则不建议为了功能对齐而增加概念。
- 纸箱没有独立领料申请，需要先决定是否引入申请单，或直接按订单行组套。

### 4. 单位主数据与换算依据（B，约 3–4 人日）

**布料实现**：`FabricMasterRecord` 支持 `UNIT` 和换算记录（物料、库存单位、计价单位、比例、依据、适用条件、生效日期）；换算目前只保存、不参与收发计算。

**纸箱现状**：纸品行的单位是文本字段，没有单位主数据，也没有换算依据；不同单位靠人工保证不混算。

**复制方式**：
- 复制“单位编码/名称/状态 + 换算记录”的资料模型和 `FabricMasterWorkspace.vue` 的单位页签交互。
- 先只做资料统一和校验，不自动换算库存；纸箱的“张/令/件/卷”等口径需要业务确认后再启用计算。

### 5. 质检限制出库（C，约 2–4 人日，按需）

**布料实现**：历史 `HOLD/REJECTED` 批次禁止出库/加工/包装，但允许调仓并保留限制；新质检写入已停止，质检归 QC 模块。

**纸箱现状**：收料可记录破损/拒收数量，但没有“批次质量状态限制出库”的通用机制。

**复制方式**：如果纸箱需要“待检/不合格纸品不得领用”，可复制布料的批次状态与出库拦截点；不要复制布料的 QC 历史字段和“仓库不再质检”的结论，纸箱的质检责任需另行确认。

### 6. 请求恢复与精确小数工具（A，约 0.5 人日）

**布料实现**：
- `requestIdentity.ts`：按账号/会话生成稳定请求 ID。
- `pendingFabricRequests.ts`：保存未确认的提交，刷新后继续核对原结果。
- `receiptQuantities.ts`、`operations.ts` 的 `sumQuantities/remaining`：前端精确小数展示，不用浮点。

**复制方式**：这些是通用工具，可直接复制到纸箱的新弹窗/新页面；纸箱已有 `request_id` 的服务端契约，前端恢复逻辑可以补齐。

### 7. 不建议复制：布料采购解析、缸号/卷号规则、裁床接口（D）

金蝶物料跟踪表的页签识别、补数身份、起始待收推断，以及“布料必填缸号、辅料不填”的规则，都是布料领域事实。纸箱供应商协同有自己的送货单和价格体系，复制这些只会增加两套互相冲突的来源。

## 六、不能复制或不建议复制的部分

| 对象 | 原因 |
| --- | --- |
| 库存表/流水表 | 纸箱库存键含客户、合同、货号、纸品、规格、单位，并按币种计价；布料含批次、缸号、卷号。合并会破坏厂区隔离和历史追溯。 |
| 纸箱客户月结/应付 | 与布料“数量仓、价格仅参考”的定位冲突；会把采购应付职责带进仓库。 |
| 纸箱供应商门户/箱唛 | 纸箱专属协作流程，布料没有对应上游。 |
| 布料采购跟踪解析 | 金蝶表结构、补数、退货页签是布料专属；纸箱已有订单/送货单来源。 |
| 布料缸号/卷号规则 | 纸箱纸品没有缸号概念；辅料/线的例外也不适用。 |
| 两边权限码 | `carton_procurement:*` 与 `fabric_operations:*` 不能互相授予；复制接口必须重新挂权限。 |
| 两边厂区锁 | 纸箱按 `carton-inventory` 锁，布料按 `FabricProcurementState` 厂区行锁；共用锁会制造无谓串行。 |

## 七、共性资产与抽取建议

### 已经共用或可以直接共用的前端组件

- `src/components/CartonSelectionSummary.vue`：布料页面已在用（`WarehousePage.vue`），可考虑改名为通用选择摘要并移到 `components/common/`。
- `src/components/DateRangeFilter.vue`、`src/components/ui/*`、`StatusPill`：两边已共用。
- `CartonFilterBar.vue`、`CartonActionNotice.vue`、`CartonSourceLinks.vue`、`CartonInventoryProgress.vue`：无业务依赖，可在第三次使用时再抽取，避免提前抽象。
- `CartonLocationPicker.vue` 与 `WarehouseLocationPicker.vue`：交互相近但数据源不同；先统一交互规范，不急着合并组件。

### 可以共享的后端工具

- 时间/日期边界：`app/core/time.py`、`carton_query.date_bounds` 与布料现有实现可收敛为一个只读工具。
- 精确小数：布料 `Decimal` + `format(value, 'f')` 的做法可直接用于纸箱新接口。
- 请求幂等：两边都已实现“request_id + 操作者 + 内容哈希 + 版本”，但存储和恢复方式不同；先共享“校验顺序”，不共享表。
- 文件任务：`carton_file_jobs.py` 只适合纸箱的导入/导出；布料若需要，复制结构而不是 import 纸箱模块。

### 不建议做的“通用仓库平台”

`docs/business/warehouse-framework-reuse-plan.md` 已明确：先复用页面模板、通用交互和控制机制，业务规则各自实现；不要提前建设可任意配置审批、库存和公式的平台。本分析与该方向一致。两仓的差异不是配置项，而是领域对象；把客户、缸号、币种、批次塞进一个“仓库类型”配置表，会让后续每次业务变化都变成框架改动。

| 阶段 | 事项 | 价值 | 风险/前置 |
| --- | --- | --- | --- |
| 1 | 布料期初整批撤销 | 高（导错可恢复） | 需要明确“撤销后重新导入”的凭证关系；不涉及金额 |
| 1 | 布料送货单/收料单打印（借纸箱纯函数） | 中（现场签收） | 纯前端，无库存写入 |

| 2 | 纸箱手机端收料/出库弹窗 | 高（现场可用） | 只改样式与布局，不改业务逻辑 |
| 2 | 布料异常工单（短收/超收） | 中（闭环） | 先限定两类来源，避免通用化 |
| 3 | 纸箱扫码定位送货单 | 中（提速） | 依赖二维码打印与供应商配合 |

## 九、风险与验证要求

1. **权限不能顺带扩大**：复制接口时必须沿用目标仓的权限族和厂区/部门范围；布料资料写入当前走 `fabric_warehouse:import`，不要因为复制纸箱接口而新增 `fabric_operations:master` 授权。
2. **厂区边界**：布料代码固定 `huakang-c`，纸箱是多厂区。把纸箱逻辑搬进布料时要去掉多厂区分支；把布料逻辑搬进纸箱时要把 `FACTORY` 参数化，并保留厂区隔离测试。
3. **写入路径要全覆盖**：锁账、盘点复核、期初撤销都会影响多条写入路径；必须同时覆盖采购实收、日常收发、期初、盘点、冲销，漏一条就会出现绕过。
4. **不可变账本**：所有更正都应追加记录，不覆盖原单；复制纸箱功能时不要把“删除/覆盖”习惯带进布料的追加账本。
5. **性能**：布料当前是全量重放 + 前端筛选；在加锁账/日志/导出前，先补服务端分页或投影，否则数据量上来会拖慢所有页面。
6. **验证**：前端至少跑 `npm run build`、相关 `npm run test:unit -- <paths>`；后端按现有 pytest 覆盖权限、幂等、并发、迁移回退；涉及页面的改动按项目前端流程做实际渲染检查，手机布局需在真实视口核对，不以桌面缩放代替。
7. **现场验收**：手机触控、扫码、打印都涉及真实设备和纸张，浏览器预览不等于现场通过；上线前需仓库实际试用。
