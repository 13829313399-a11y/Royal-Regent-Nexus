# Legacy QC inspection implementation

These are the retained backend/history contracts of `/api/qc-inspections`. The old frontend has been replaced by QC_department; this document does not describe the active entry.

### QC Department Inspection Operations

The current target business requirements are `docs/business/QC验货运营中心业务需求.md`, reorganized from the user's `QC完整业务流程.docx` and latest explicit direction. The target removes report renaming from this center, moves temporary-order creation into an optional modal/drawer action within the total inspection schedule, adds customer filtering there, and supports checkbox-based bulk import of selected preview rows with unselected rows left pending. The frontend now implements these entry changes in QcOperationsCenterView/QcScheduleWorkspace: the old center, standalone manual-order page and rename page are removed. The four top-level entries are total schedule, schedule details, problem handling and reports. Total schedule is now an import/manual-add overview, without an inline order table. The standalone `/schedule-details` table includes only confirmed SCHEDULE_IMPORT orders that are unfinished and not cancelled; unscheduled and IN_PROGRESS/PENDING rows remain visible, while completed results (including FAIL) leave the pending table. It loads all factory weeks but opens on the current Asia/Shanghai calendar day. Pending schedules are grouped into one full table per effective inspection date, with previous/next/today, date-range, all-date and undated views; no day is split across row pagination. Customer/date/status/agency filters and optional current-business-week filtering are supported, plus revision-checked schedule editing. Result writers can select rows, an entire day or every filtered row (including days not yet expanded) and batch-register a shared explicit result and actual date. Filter changes clear selection. The confirmation dialog lists orders, requires a new-event type and note, preserves existing pending-event details/type, and saves each order independently with stable retry request IDs. Successful results leave the pending view; partial failures remain visible for retry. Event create/update accepts an optional expected_pending_order_revision guard, which enforces the imported-pending scope and checks order revision before mutation; the existing result-write and factory checks remain authoritative. No actual inspected quantities, sampling standards or dispositions are inferred for new quick-entry events. Manual orders and completed/cancelled history remain accessible through the separate `/order-records` table; source and completion filtering does not delete records. Import selection spans pages and filters, supports explicit KEEP/SKIP as well as CREATE/UPDATE, and submits at most 1000 decisions sequentially using returned revisions; unselected rows stay pending and existing current-week batches can be resumed. Legacy add links open the schedule modal; rename links redirect to reports. Persistence and historical attachments are preserved. This is not a claim that every target report layout or future configuration screen is implemented. The earlier `docs/business/qc-complete-business-process.md` remains a reference for historical implementation and technical contracts; its conflicting product-direction statements are superseded by the new requirements. Reporting week boundaries, customer/market mapping, staged inspection dates and metric definitions remain explicit business confirmation items.

QC schedule imports use the explicit `qc-review-unshipped-v1` rule: read only `正单评审表`, only rows with order type `正单` or `正式PO` above its standalone `取消单` section marker. The user defines that region as unshipped orders. Never fall back to `接单表`, ITEM sheets, cancelled rows or shipped sections; missing review sheet, order-type header or cancellation boundary blocks preview. No automatic calendar-week filtering is applied to this source region; the selected business week is assigned only on explicit QC confirmation. Header aliases cover `客名`, `Contract No.`, `P/O#:`, `产品编号`, `數量`, `验货日期` and `客要求走货期`. Customer/market names and national standards are not inferred as export country codes. Preview retains original Sheet/row and mapped source-cell values, preserves identifier leading zeroes, and flags missing PO or multi-stage date text for correction/skip rather than guessing. Formal orders require explicit confirmation of selected rows; bulk confirmation never includes unselected rows. Effective planned inspection dates use the explicit customer/planned date first, then shipment date when the former is blank; only two blank dates remain unscheduled. Raw planned dates and import source cells are preserved instead of backfilled, so later shipment changes automatically update fallback schedules. Frontend display, planned-date filtering, status/counts and ascending order, backend order sorting, and newly generated schedule XLSX period selection/date cells share this rule. Nonempty invalid or multi-stage text remains a validation issue, never a missing-date fallback. Existing orders apply the rule without migration; prior report snapshots remain immutable.

The canonical QC workflow and implemented business rules are recorded in `docs/business/qc-complete-business-process.md`. The module is registered at `/modules/qc/inspection-operations`, uses `/api/qc-inspections`, and is backed by Alembic revision `20260824_0082` (following the P0 revision `20260812_0067`). Its persisted core includes customer configuration, schedule-import batches and rows, inspection orders, multiple inspection/reinspection events, event PO/item lines, defects, test results, explicit dispositions, inspection report packages/documents, inspection problems, schedule decisions, generated report snapshots, report-renaming batches/groups/source files, audit events and idempotency records. The implementation is present in the repository but must not be described as deployed until the migration is applied and the application services are restarted and verified. QC schedule imports accept `.xls`, `.xlsx` and `.xlsm` workbooks up to 35 MB per file; the API streaming read and the import service both enforce the same authoritative cap.

Every inspection order has a system-generated factory-scoped unique inspection number. Sales contract plus customer item number is candidate matching only; zero matches may create a new order, one match may be compared, and multiple matches require a user decision with no silent overwrite. Temporary orders require a PO. Inspection results are entered on the order detail or through selected pending orders in the daily schedule’s batch-result dialog; both persist inspection events. Initial `PENDING` is not a submitted result and creates no problem; submitted `FAIL`, `REJECTED`, `CONDITIONAL_PASS` or `CANCELLED`, or a manual problem flag including PASS plus that flag, creates a deduplicated problem draft. Problem description, return reason, corrective action and resolution are maintained only in the problem workspace.

The QC permission family has 12 codes: read, schedule write, order write, result write, problem write, report export, rename preview, rename execute, customer management, audit read, factory summary and group summary. Inspector permissions include all normal factory operations, including rename execution and own-factory report export. Supervisors and managers additionally receive customer management, audit read and factory-summary permissions. `qc_inspection:group_summary` is separately granted, requires global factory scope, and is not inherited by the QC manager role. Backend factory checks are authoritative.

Current reports are manual XLSX outputs for customer summary, weekly statistics, Huaxing customer weekly detail, Huaxing weekly aggregate and group summary; PDF, CSV and scheduled generation are not implemented. Customer-summary Sheets are derived from the factory's active customer configurations, retaining an empty formatted Sheet for configured customers without completed inspections while also including unconfigured customer names that have reportable data; the historical 12-name sample list is not hard-coded. Inspection orders model packing, carton count, report status and production department; problems model first and second responsible persons. The report builder reads only those authoritative fields and leaves missing historical values blank. The Huaxing weekly detail column for non-return rework/AOD remains blank because no authoritative field exists and must not be inferred from results or problem text. Report renaming is removed from this frontend, including its API client and permissions references. Its historical backend remains for compatibility and retains explicit groups and immutable source uploads, preview-before-execute, audit and idempotency, and produces a new ZIP rather than mutating originals. Non-Caixing names are `COUNTRY_customer-item_PO_YYYYMMDD`; Caixing names are `report_customer-item_PO_digits-only-quantity_YYYYMMDD`; multi-image JPGs use `_01`, `_02`, `.jpg` and `.jpeg` inputs are accepted, illegal filename characters normalize to `_`, and a missing PDF/JPG or any group error leaves the whole group unchanged while other groups continue. A batch is capped at 39 groups, 25 files per group, 25 MB per file and 250 MB total; production gateways must also enforce a request-body cap no higher than 250 MB because application validation cannot replace ingress and temporary-disk protection. Multi-PO/multi-item naming remains unresolved and must not be inferred.

The V3 QC requirements baseline is evidence-driven from the read-only 2026-08-24 review of the user's QC archive (7,950 files, about 8.06 GiB). It distinguishes structured source data, system-generated statistics, immutable externally issued reports, and evidence/adjacent quality registers. V3.1 implements the P1 core transaction chain: an inspection order can keep multiple execution/reinspection events; each event has multi-PO/item lines, defects, tests and explicit return/rework/AOD/concession dispositions; saving an event synchronizes the order's latest result without overwriting event history; a per-event XLSX inspection report contains conclusion, PO/item, defect, test and disposition sheets and creates a generated report package/document index. External original-file upload/migration, OCR, field-level raw-data lineage, cross-report automatic reconciliation and final-report approval remain requirements only. P2 still covers department nonconformance, product testing, approved samples, training and factory-audit registers only if ownership is later confirmed.

The V3.1 report catalog preserves the five current manual XLSX outputs and implements weekly schedule, daily inspection ledger, weekly problem detail, weekly return summary, inspection pass-rate, annual statistics, product-quality ledger and inspection-document index XLSX outputs, plus a per-event inspection report. Report snapshots record explicit WEEK/MONTH/YEAR/EVENT scope, `qc-metrics-v1`, source revision SHA-256 and artifact SHA-256. New return reports count only explicit `RETURN` dispositions; FAIL/REJECTED do not imply return, CONDITIONAL_PASS does not imply AOD, reinspection does not overwrite the first event, and zero denominators emit zero rather than spreadsheet errors. The metric dictionary still needs business sign-off. Full evidence archiving must later support PDF-only, image-only, mixed/multi-PDF packages plus read-only historical DOC/DOCX/XLS/XLSX attachments using immutable originals, relative source path and content hash. This broader archive requirement does not reactivate the retired rename UI; the retained historical backend still uses explicit one-PDF-plus-JPG/JPEG groups with the existing size/count limits and single-PO naming; multi-PO/multi-item naming still requires business sign-off.
