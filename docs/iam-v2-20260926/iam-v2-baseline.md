# 人员与权限 V2：基线与实施计划

基线：`a4720a52`；开始时工作区干净。开发输入来自用户提供的 IAM V2 开发包；其中表名和接口属于设计要求，不能当作已实现事实。

## 已核实的影响图

- `services/iam.py` 的 `preview_system_position` / `commit_system_position` 使用人员原主厂区，清理普通角色和一般 override；`_position_cleanup_overrides` 仅特别保留三项 supplier 权限。V2 人员必须拒绝这个入口。
- `EmployeeProfile` 是单主组织投影；`management` 是总务部门，六个厂区已存在。集团职能组织不进入生产厂区白名单。
- `auth.py` 每次请求构造数据库授权上下文；canonical deny 先于管理员和 allow。普通写入要求 enforce；supplier 窄例外保持。
- `iam.py`、`system.py` 多个公共服务自行 commit。新变更服务不能嵌套调用这些提交入口。
- 主组织消费者包括 auth、system、iam、directory、internal_quote、customer_price_settings、business_authz 和 molding_sample。报价销售资格不能由宽权限推断。
- 停用当前没有完整撤会话闭环。left 必须阻断旧 active 入口；复职使用新 epoch。
- requests/audit 前端路由当前重定向 roles，需要真实办理和记录页。
- Alembic 当前末端为 `20260924_0124`；数据库状态尚未读取，不对本地业务库或生产库执行迁移。

## 实施顺序

1. P1：扩展结构、组织、任职解析、冻结权限包快照和来源外键；只读预检、显式映射迁移。
2. P2：严格草稿、依赖版本预览、幂等原子提交，来源隔离、旧 writer 收敛。
3. P3：保留注册审核和供应商管理，增加人员详情、变更向导、记录与交接入口。
4. P4：兼任支援、冻结/离职/复职、正式业务资格。
5. P5：服务器时间解析、预约取消、角色版本升级和通知/交接重试。
6. P6：隔离 SQLite 迁移与回滚、真实 PostgreSQL 竞争（环境可用时）、原业务回归及浏览器验证。
7. P7：逐项验收矩阵和迁移/回退交接。未完成能力保持关闭，不把结构或单测当作生产验收。

## 兼容决策

- 旧数组接口保持；新增分页人员资源。identity_mode 与 AUTHZ_MODE 分开。
- 迁移保留真实权限定义与跨厂语义，来源需明确映射；不按中文职位或第一个 role 猜测。
- 保留既有 user_manage / access_manage 的职责；地方转授需要明确上限，业务权限不是转授权限。
- 全部 IAM 写入遵守同一数据库互斥顺序，重新读取 actor。SQLite 写锁与 PostgreSQL 行锁分别验证。
- V2 权限包绑定使用不可变快照；全局 inactive 与 deny 仍优先。关闭新写入不能退回旧授权兜底。

## 交接覆盖待核实清单

| 模块 | 已核实入口 / 处理原则 |
|---|---|
| 内部报价 | `business_owner_id` 是指定审核负责人；按真实可修改状态、header revision 和销售资格接管 |
| 啤办 / 生产任务 | 核实当前责任字段；历史创建、审核和完成事实保持 |
| 仓库 / 纸箱 / 订单 | 核实个人责任与角色队列；禁止变库存与历史流水 |
| 3D / UV / 喷油 | 核实未完成个人责任；不改变机器归属或发送设备命令 |
| 注册 / 找回密码 | 管理范围队列，仍由原审批服务办理 |
| 供应商 | 保留独立用户权限和业务边界；不恢复 SupplierMember 授权 |

未核实/未适配的模块必须返回未覆盖，不能返回零项完成。现有旧全清理测试只继续适用于 legacy；新增 V2 拒绝/来源保留回归，不能直接删断言。
