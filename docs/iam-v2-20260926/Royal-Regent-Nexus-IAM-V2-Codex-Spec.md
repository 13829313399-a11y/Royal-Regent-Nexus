## 1. 本次设计结论

### 1.1 不推倒 IAM，补齐“人员任职生命周期”

采用：**账号 + 正式任职 + 权限包 + 明确业务范围 + 有效期 + 变更单 + 工作交接**。

管理员日常看到的是“调到哪个厂、担任什么岗位、开始哪天、哪些工作交给谁”，不是上百个权限勾选项。底层仍使用现有细粒度权限，并能解释每项权利来自哪里、何时结束、为什么不能操作。

### 1.2 五项架构决策

1. `AuthUser.id` 是长期身份。调厂、改岗、复职不删除账号、不新建账号来规避流程。
2. 用户填写的“职位名称”只是申报信息；正式任职与权限包是管理员确认的两个独立概念。
3. 一个人可以有一个主职、多个兼任/临时任职。结束一个任职只处理其关联授权，不清空整个人。
4. 业务单据的所属厂区、创建人和既有审批证据不随人员调动改变。工作责任交接是独立、可追溯的动作。
5. 预览、审批和执行使用同一规范化变更内容；旧入口必须接入同一写入服务，不能留下绕过新规则的通道。

### 1.3 不做两种极端

不做“改一个厂区字段就算调动”的简化，也不做所有操作都要多人逐级签字的重型人事平台。常规、权限范围内的管理员操作通过一个简明向导直接确认；跨范围、系统管理权和实际业务阻塞才升级处理。

### 2.1 三个不能忽略的细节

**第一，旧行为部分是明确测试过的契约。** 例如现有测试允许“正式部门仍是工程，但授予生产类内置权限包”。不能把它简单判为脏数据，也不能自动把人员部门改成权限包部门。

**第二，停用不是离职。** 当前停用请求会让后续请求因账号不可用被拒绝；但该路径没有直接撤销已有会话。若恢复为 active 且原会话仍有效，原 Cookie 是否恢复可用需要新增测试确认并按新契约修正。不能把停用按钮包装成完整离职流程。

**第三，授权模式尚有过渡机制。** `legacy`、`shadow`、`enforce` 的行为不同；普通 IAM 配置写入受 enforce 限制，供应商三项权限另有窄例外。本文不假定生产已经 enforce。

建议组织展示：集团下有六个厂区，并可展示一个“集团总务”职能节点；每个厂区也可以保留实际存在的本厂总务部门。**不把当前所有 `management` 用户自动搬到集团。**

新增集团总务正式归属时，使用独立组织节点，例如 `group-management`，类型 `functional_unit`，部门代码仍为 `management`；这个新节点是 V2 提案，当前注册接口只接受六个具体厂区，不能直接传入它后宣称兼容。

集团总务人员可默认进入 `group` 总览；其业务操作范围仍需明确选“华康A、华康B”或经授权的全部现有厂区。不能因所属总务自动获得所有业务或 `system:*`。

### 3.2 目录与业务能力分离

组织目录说明“人属于哪里”；模块能力目录说明“某厂有哪些模块、哪些功能已启用”。

- 六个厂区都可以进入人员管理，不表示注塑、UV、喷油、3D 功能对六厂全部开放。
- 新权限不能绕过模块启用开关、实际设备控制开关及模块原有适用厂区限制。
- `src/data/enterpriseMock.ts` 只可作为旧展示目录的迁移参考，不能作为生产业务权威。
- V2 提供后端权威组织/部门查询；注册、审核、用户筛选、任职编辑共用其响应。
- 保留 `production/molding`、`pmc-warehouse/warehouse` 等已存在历史别名的明确映射；不全库批量替换旧业务字段。
- 新增厂区/部门可登记组织资料；新厂业务能力仍需单独建设，登记组织不自动生成任何业务数据或角色授权。

## 4. 把“职位”拆成可理解的业务对象

| 对象 | 含义 | 谁可改 | 是否直接产生权限 |
|---|---|---|---|
| 账号 | 这个人在系统中的长期登录身份 | 管理员及既有账号流程 | 否 |
| 用户申报职位 | 注册时本人填写的工作描述 | 用户提交，审核时保留原文 | 否 |
| 正式职位名称 | 管理员确认的岗位名称，如“仓库主管” | 有人员管理权者 | 否，需配套授权 |
| 正式任职 | 某人在某组织/部门以某职务工作的一段时间 | 人员任职流程 | 作为授权来源和业务资格依据 |
| 权限包 | 内置系统职位或自定义角色所包含的操作能力 | 内置代码维护；自定义由权限管理员维护 | 绑定后才生效 |
| 业务作用范围 | 哪些厂区、部门和已支持的具体资源 | 授权管理者 | 限定权限 |
| 个人例外 | 对特定权限单独允许或明确禁止 | 授权管理者 | 在明确范围/时效内生效 |
| 管理范围 | 管理员可以管理谁、授予哪些权限及最大范围 | 集团管理员 | 不等同于本人业务操作权 |

### 4.1 主职、兼任、支援

一人同一时刻最多一个主职；可以没有有效主职（待入职、离职、资料待核实），不能假造一个厂区填满字段。兼职和临时支援可以多个。

示例：

```text
张某（示例账号，非读取的真实用户）
├─ 主职：华康A / 仓库 / 仓管员
│  └─ 授权：华康A仓库相关操作
├─ 兼任：华康B / 仓库 / 盘点协助
│  └─ 授权：华康B已明确允许的盘点操作
└─ 临时支援：华兴 / 仓库 / 收货协助，10月1日至10月8日前
   └─ 授权：所选收货权限，至期自动失效
```

不能因此得到华兴所有仓库权限，更不能把“可操作的厂区集合 × 可操作的部门集合”做笛卡尔积。

### 4.2 一段任职可以绑定多个权限包

正式职位与权限包不强求同名。管理员可以给某正式岗位组合多个已审定权限包，但预览必须清楚显示每个包的实际范围。

仅给工程人员补充一种生产操作能力，不自动说明此人已正式调入生产部。反之，只有正式销售任职且满足报价模块现有规则的人，才可作为销售审核候选；仅拥有宽泛管理员权限不等于销售身份。

### 4.3 独立授权不能被任职变更误删

授权来源至少区分：

- `assignment`：随具体任职终止或到期而失效。
- `temporary_support`：来源于临时支援任职，不独立无限延续。
- `individual_exception`：经批准的个人例外，明确是否关联任职。
- `external_collaboration`：例如现有供应商协同权限，保留独立业务边界。
- `system_administration`：系统管理权，独立管理，不能由“总经理”推导。
- `legacy_unclassified`：历史来源待核实，不能猜测应归哪个岗位。

`source_type/source_id` 用于追溯；真正的任职关联使用外键，不能只靠自由字符串推断权限生命周期。

## 5. 权限计算契约

### 5.1 最终决策

```text
允许操作 =
  账号当前可用
  AND 权限已登记且有效
  AND 资源/模块业务条件允许
  AND 不存在当前作用范围内的有效明确禁止
  AND 至少存在一条完整匹配的有效授权来源
  AND 满足该业务自己的身份、负责人和流程状态要求
```

“一条完整匹配”必须把权限、任职来源、厂区、部门、资源范围、有效期连接在同一条证据链上。多个允许来源可以取并集，但不能把来自不同来源的条件拼成一条从未被授予的权利。

示例：甲拥有 A厂仓库授权和 B厂业务授权，不产生 A厂业务授权或 B厂仓库授权。

### 5.2 判定顺序与现有特例

1. 验证账号/会话和请求中的真实资源所属厂区，不能相信前端单独传来的厂区标签。
2. 检查权限注册状态和模块适用条件。
3. 匹配有效 `deny`。延续当前 deny 优先于普通 allow 和 wildcard 管理员的规范行为。
4. 计算有效管理员、个人 allow、角色/任职来源。
5. 执行现有业务谓词，例如可审核身份、单据状态、成本可见、供应商归属、设备控制开关。
6. 返回允许/拒绝及可解释原因；实际数据查询也按相同范围约束。

未知权限默认拒绝；不能把空权限目录解释为“所有权限均可”。不要以 GET 就认定只读，也不要让跨厂只读带出成本、批量导出或审批能力。

保留并专门回归：内置职位的啤办生产任务跨厂只读、仓库经理特定跨厂操作、总经理不自动获得系统管理权、供应商三项独立权限、总务/工程/生产现有审批边界。

### 5.3 范围不能只能“本厂或全部厂”

新增界面支持：本任职厂区、选择若干厂区、全部现有适用厂区。所有范围最终编译成后端可审查的明确授权元组。

- `home`：以来源任职的厂区为锚点，不以用户当前下拉框或后来改变的主厂区为锚点。
- `selected`：显式有限集合，例如 A、B；不自动包含未来新增工厂。
- `all_current`：批准时展开并保存现有适用厂区集合；未来新增工厂须扩展审批。
- 历史特殊 `*`：为现有管理员/业务特例保留，单独展示，不把它静默转换为普通选厂。

新 V2 绑定的范围上限必须在当前 `system_position_grant_scope_source` 等跨厂扩展之前约束。一个具有跨厂能力的权限包，不能绕过此绑定被批准的范围上限。历史绑定迁移时必须显式保留原有扩展语义，不能因此无声缩水或扩权。

### 5.4 明确禁止的处理

解除某个 allow 不等于新增 deny；恢复“继承”不等于授予权限。

- 任职派生 allow：来源任职结束即失效。
- 关联该任职的局部 deny：只在原范围内有效，其结束策略在变更预览中显式列出。
- 用户级持续 deny：默认保留，不因调岗/换厂而清除。
- 来源不清的历史 deny：按原范围保留，待有权限人员明确处理。
- 把旧厂 deny 自动复制到新厂也不正确；是否新增新范围限制需单独批准。

“复制同事权限”只能复制经审核的岗位/权限包与范围建议，不能复制对方的独立 allow、deny、管理员权限、供应商身份或未到期临时授权。

### 5.5 行级交接访问只在已适配模块开放

交接期不默认保留旧厂完整岗位。支持两种明确选择：不保留旧权；或保留有限期限、有限动作、明确单据集合的交接授权。

后者必须由该业务模块实际支持服务端单据集合过滤。未适配模块显示“不支持限定单据交接授权，请转交责任人或使用原业务流程”，不能仅前端过滤后给整厂权限。

## 6. 业务情境与默认规则

| 场景 | 处理方式 | 必须验证 |
|---|---|---|
| 注册填写“主管”，管理员认定为文员 | 保留申报原文，正式确认文员任职与权限包 | 文字不直接授权 |
| 正式职位错别字/姓名更正 | 资料更正事件 | 不改变权限包/组织 |
| 同厂晋升或降岗 | 结束原任职，新增继任任职 | 新旧权差异、个人例外归属 |
| 同厂跨部门 | 显式变更正式部门，处理业务资格 | 不只换权限包 |
| A厂调到B厂，同岗位 | 新任职锚定B，结束A来源权限 | 历史A单据不搬厂 |
| A厂工程调到华兴仓库 | 同时变更组织、部门、正式职位、授权包 | 一次预览、一次一致性提交 |
| A主职+B兼职 | 添加独立兼任任职 | 不替换A主职，不交叉串权 |
| 借调后回原岗 | 临时任职/主职时间段明确，预先安排返回段或保留原主职 | 不能自动恢复已撤销例外 |
| 临时代理主管 | 批准限定的代理权限及时间 | 不复制原主管账号、不共享密码 |
| 原主管中途离职 | 代理来源相关资格重新校验/终止 | 依赖来源的授权不能继续“悬空” |
| 总务属于本厂 | 保留本厂 management 任职 | 不搬到集团节点 |
| 集团总务服务多个厂 | 职能组织归属 + 明确多个操作厂区 | 组织归属不等于全厂操作 |
| 主职调动但保留供应商协同 | 只结束原主职来源 | 供应商三项及供应商数据隔离不变 |
| 停用/冻结账号 | 立即阻止使用并撤销全部会话 | 恢复后旧Cookie不能复活 |
| 离职但交接未完成 | 立即停止账号与内部授权，工作进入待接管 | 不因交接未完成允许离职者继续登录 |
| 复职 | 同一账号重新审批新的任职段，重新登录 | 不一键复活历史临时权/管理员权 |
| 临时权限自然到期 | 后端每次请求按时间判断 | 定时任务停了仍失效 |
| 未来调动取消 | 生效前基于版本撤销计划并恢复被该计划改动的时间段 | 不覆盖之后的其他变更 |
| 已生效调动撤回 | 发起反向变更/新任职段 | 不是删除历史或数据库回滚 |
| 两个管理员同时调同一人 | 版本/锁保证最多一个成功 | 另一个409后重新预览 |
| 批量同岗调厂 | 逐人预览、逐人原子提交，批次汇总 | 不隐瞒失败，不重复已成功者 |
| 两名员工互换需要全成全败 | 显式小规模联动事务，按用户ID排序加锁 | 不能伪称普通批次天然全原子 |
| 岗位权限包升级 | 版本化发布，展示影响人数与新增/减少能力 | 不静默扩权，不覆盖个人deny |
| 厂区/部门改名 | 更新显示名，稳定ID不变 | 不重写历史快照 |
| 部门撤销/合并 | 先迁移任职，停止新选用，保留历史 | 不是硬删被引用组织 |
| 新增模块或工厂 | 目录变更与授权变更分开 | 不把all_current自动扩大 |
| 没有正式主组织的历史账号 | 资料待确认队列 | 不取第一个角色推断主厂区 |
| 自己管理自己的权限 | 普通提权必须独立有权人员处理 | 超管应急例外单独记录，不假装双人审核 |
| 最后一个超管被停用/到期 | 全局管理员不变量校验 | 并发下仍不能造成无人管理 |
| 修改权限包但正式部门不变 | 明确“补充能力”，非调岗 | 不绕过销售等真实业务资格 |

## 7. 面向管理员的办理流程

### 7.1 注册与入职

```text
用户提交申报资料
→ 待审核队列（不产生业务权限）
→ 管理员核对姓名/组织/部门/正式职位
→ 选择建议权限包及范围，展示实际能力
→ 预览首次任职与权限
→ 有权管理员批准
→ 同一事务激活账号、建立任职、绑定授权、记录审计
→ 通知用户，登录进入正式主组织对应首页
```

继续使用现有注册申请，不建立第二套注册系统。原始申报值和审核后的正式值分开记录；建议权限包只是建议，不能根据“经理”等关键词自动批准。

审批时先检查操作者对目标组织、实际权限包和完整扩展范围是否都有授予权。管理员修改注册者的厂区后，审批权限必须依据纠正后的范围重新检查。

### 7.2 任职变更：一个向导，按复杂度逐步展开

**第1步：选择变更类型。** 调厂调岗、增加兼任、临时支援、正式资料更正、冻结、离职、复职。

**第2步：确定新任职。** 组织、正式部门、正式职位、主职/兼任、权限包、生效时间。界面分别说明“人事归属”和“权限包作用部门”，不能混为一个下拉框。

**第3步：查看影响。** 新增权限、取消权限、保留授权、待明确来源、工作交接、登录首页变化。同岗位调厂可默认复用合规权限包，但仍显示新范围，不自动继承个人例外。

**第4步：确认办理。** 普通有权变更直接生效；需要审核的进入待审核；预约办理展示确切日期和时区。保留可编辑原因，避免普通动作要求重复写长篇说明。

最常见“同厂正常换岗、无待交接、无例外”的流程可以合并第2/3步在同屏完成。不能为了结构完整强迫每个用户点很多无意义的下一步。

### 7.3 必须显式决定的旧授权

变更预览中，把旧授权分为：

| 分组 | 默认动作 |
|---|---|
| 来自被结束任职的普通授权 | 随该任职结束 |
| 来自其他仍有效任职的授权 | 保留 |
| 个人独立allow | 展示，管理员选择保留/终止；不静默扩展到新厂 |
| 用户级deny | 按原范围保留；另行解除需明确操作 |
| 供应商独立协同授权 | 调岗默认保留；离职默认随账号整体终止 |
| 系统管理员授权 | 单独展示，不通过普通职位替换修改 |
| 未来授权/未来调动计划 | 检查是否冲突，显式取消或调整 |
| 来源不明历史授权 | 转入核实队列；正式转V2前解决对应归属 |

禁止“清理历史权限”按钮默认全选全部记录。确需历史整改时，独立展示每一条变化与实际增减权结果。

### 7.4 审批：以真正需要为准

默认采用“已有权限范围内的管理员直接确认”。跨厂变更默认由有完整范围的集团管理员处理，不强制源厂、目标厂、人事、总经理四层签字。

未来启用地方管理员联合审核时，所有必需管理范围都必须被覆盖；两位管理员的确认不能被拼接成任一方都无权授予的系统特权。

普通操作者不能批准自己的提权；具有操作能力也不等于有权转授。真正高风险动作明确二次确认；组织/岗位文字更正无需按提权处理。

若系统只有一个集团超管，允许其在自身已拥有的权限边界内完成受审计的直接管理；涉及自身提权/创建新的超管权限来源时，不得虚构第二审批人。保留清楚标注的受控应急流程或要求另一实际管理员办理，不设计会把系统永久锁死的“必须不存在的第二人批准”。

## 8. 工作交接：权限变更不能让待办失踪

### 8.1 两条状态线，不混在一起

```text
身份/授权状态：待审核 → 已安排/已生效 → 已结束
工作交接状态：未评估 → 无需交接 / 待分配 → 交接中 → 完成 / 需人工处理
```

“权限已变更”不等于“所有业务交接完成”。界面允许显示“调动已生效，仍有2项待接管”。离职与冻结必须立即阻止账号使用，不能被业务交接阻塞。

### 8.2 永远保留的历史事实

不批量修改 `created_by`、历史审批人、已签发文档、历史审核意见、原所属厂区、库存流水、成本快照、机器连接归属。

需要修改的是仍可变的当前责任字段，例如当前跟进人、当前审核候选、未完成任务承接人。字段和可修改状态必须由相应业务模块确认，不能凭名称猜测。

### 8.3 模块适配器契约

建议在 `backend/app/services/identity_handover/` 建立明确注册的模块适配器。不要写“遍历数据库所有 *_user_id 字段并替换”的通用脚本。

```python
class HandoverAdapter(Protocol):
    def list_open_responsibilities(self, db, subject_id, affected_scope): ...
    def validate_successor(self, db, item, successor_id, effective_at): ...
    def apply_reassignment(self, db, item, successor_id, expected_revision): ...
    def verify_result(self, db, item_id): ...
```

适配器必须返回：模块、稳定对象ID、原厂区、当前状态、原责任人、候选接管人、是否阻塞、对象版本、可执行操作。以上是接口设计示意，Codex 必须根据真实模型补全类型和异常。

### 8.4 按现有项目优先级接入

| 对象/模块 | 必须核实与处理 | 禁止行为 |
|---|---|---|
| 内部报价 | 正式销售任职、指定业务审核人、候选列表、待审状态；复用各版本原审核规则 | 因为超管就自动变成销售审核人；统一改掉v2/v3/v4流程 |
| 啤办单/工程与生产任务 | 核实真实责任字段；角色队列重新按当前有效成员计算 | 调岗即自动审核/自动完成啤办 |
| 仓库/纸箱/订单协同 | 个人责任项可接管，部门待办按权限队列展示 | 改库存归属、改已过账人、重发采购订单 |
| 3D/UV/喷油 | 仅接入真实存在的未完成责任项；保留厂区和机器门禁 | 调岗即切换设备账号或向设备发控制指令 |
| 系统注册/找回密码待办 | 按当前管理范围重新计算候选管理员 | 仅转发通知就视为处理成功 |
| 供应商协同 | 保留既有供应商识别与服务厂区边界 | 复活已退役SupplierMember授权路径 |

对尚未适配的责任类型，显示“未覆盖，需人工检查”，不能返回“0项/已全部交接”。确实没有个人责任字段的模块可标记“采用角色队列，无需个人转移”，并在模块能力登记中给出依据。

### 8.5 交接事务与失败

同库且可在一个短事务完成的少量责任转交，可以与立即任职变更同事务提交。大批量或跨模块复杂交接使用持久化交接项，逐项幂等处理，独立显示结果。

授权停止不能等待外部设备或通知发送成功。交易内写入待交接/待通知记录，交易外处理；失败不会恢复旧权限，也不重复已经成功的责任转移。

预览后业务又新增待办时，执行需重新检查；即使审批后又出现新责任，办理中心仍应发现“原责任人已不具资格”的待接管项。普通任务候选选择和真正执行动作都要重新检验当前资格。

新接管人也调岗或停用时，接管任务回到需处理状态；不得把工作盲目转给同名用户或“列表第一个人”。

## 9. 数据模型：复用为主，少量新增

以下是推荐最小领域结构，字段名可按仓库约定调整，但关系与不变量不能丢失。新表统一单一命名体系，不同时创建 `identity_*`、`employment_*`、`iam_v2_*` 三套相同对象。

### 9.1 保留并扩展现有实体

| 现有实体 | 建议扩展 |
|---|---|
| `AuthUser` | 保留既有status；冻结/离职原因与生命周期通过变更单关联；不把自由职位写入角色字段 |
| `EmployeeProfile` | 增加 `primary_assignment_id`、`primary_org_unit_id`、`employment_status`、`employment_epoch`、`identity_version`、`identity_mode` |
| `AuthRoleBindingMetadata` | 增加 `assignment_id` FK、`role_version_id` FK、明确授权范围上限、`employment_epoch`、来源约束 |
| `AuthUserPermissionOverride` | 增加可空 `assignment_id` FK、`lifecycle_policy`、`employment_epoch`；独立deny保留来源 |
| `AuthAccessRequest` | 扩展 `request_type`、V2工作流状态、`revision`、生效时间、幂等键/摘要、类型化请求内容、交接摘要 |
| `AuthAccessRequestItem` | 继续承载变化项目，补充任职/来源关联；严格按request_type解析，不执行任意JSON指令 |
| `AuthAuthorizationPreview` | 继续使用，预览绑定完整内容及依赖版本；不另建第二种预览令牌 |
| `AuthAuthorizationEvent` | 承载人员、任职、授权、审批和交接事件；统一关联change_request_id |
| `AuthUserAuthorizationRevision` | 保留数据库变更计数；新写入同事务递增 |
| `AuthSession` | 冻结/离职撤销全部active会话；恢复不重置revoked状态 |

对于旧 `AuthAccessRequest.status`，先调查全部消费者。V2可以增加单独 `lifecycle_state`，避免老接口把新状态误作普通权限申请；旧列表明确过滤旧request_type，新列表完整展示新类型。不能两边都能批准同一个请求。

### 9.2 新增：组织节点 `IamOrgUnit`

建议字段：`id`、`code`、`name`、`kind`、`parent_id`、`legacy_factory_id`、`status`、`revision`、创建/修改时间。

- `kind`: group / factory / functional_unit。
- 六个厂区保持原ID映射；group与group-management不产生实体厂数据。
- 禁止父子循环；已被任职或业务引用的节点不能硬删。
- 部门与组织可用关系用一个明确关联表 `IamOrgDepartment`，包含组织ID、部门代码、状态、revision。已有允许选择的组合先按真实契约保留，不猜测实际设部情况。
- 目录维护权限不等于新增业务功能的权限。

### 9.3 新增：正式任职 `EmployeeAssignment`

建议字段：

| 字段 | 契约 |
|---|---|
| id / user_id | 稳定ID；指向现有账号 |
| org_unit_id | 正式组织，不允许 `*` |
| department_code | 正式部门，不因选权限包静默变化 |
| official_position_title | 管理员确认的岗位名称 |
| assignment_type | regular / part_time / temporary / acting |
| is_primary | 主职标记，与临时/长期类型独立 |
| valid_from / valid_until | 时区明确的半开区间；结束可空 |
| lifecycle_state | approved / revoked；当前/未来/已结束由时间与撤销状态派生 |
| employment_epoch | 防止离职前未来计划在复职后“复活” |
| created_by / confirmed_by | 实际操作人与确认人 |
| source_request_id | 此任职的授权变更单 |
| revision / created_at / updated_at | 乐观并发与记录时间 |
| ended_reason / revoked_at | 终止证据，不能删除原记录替代 |

同一个任职关联多个现有角色绑定，所有派生allow必须依赖任职有效性。一次转岗建立“旧任职结束 + 新任职开始”的历史，不就地覆盖原任职的组织/职位。

“资料更正”可以校正当前文字，但必须保留更正事件和前后值；真实生效过的人事变化不能伪装成文字更正。

### 9.4 新增：权限包版本 `IamRoleVersion`

建议唯一键：`(role_id, definition_hash)`；保存版本号、完整权限码集合、作用范围规则快照、来源code/database、发布日期、发布人/发布事件。

目的不是再造角色，而是让预览、预约、历史解释指向确定版本。

- 现有代码内置职位继续只读；仍通过 `system_positions.py` 与 reconciliation 更新代码定义。
- 为V2生成已验证的不可变版本快照；V2绑定读取所绑定版本，不能继续无条件读取已变化的实时 `AuthRolePermission` 而绕过版本。
- 内置目录发现新版本后，对V2显示“可升级”；批量升级走影响预览。已有旧模式账号按原reconciliation契约处理，迁移时明确界线。
- 自定义角色修改通过现有preview/commit发布新版本，选择更新哪些V2绑定；不自动覆写预约中的已批准权限快照。
- 紧急禁用某权限时，全局权限目录的inactive优先于任何旧版本；旧版本不能绕过撤权。
- 第一次迁移快照必须与当前有效权限完全一致，不把历史文档中的“理想权限包”拿来替换。

这是V2对“未来计划可重复解释”的新增设计，需修改现有模板更新回归测试并记录行为变更，不能让代码模板与数据库快照长期无提示分叉。

### 9.5 新增：交接项 `IamHandoverItem`

字段至少包括：变更单ID、adapter_key、resource_type/id、factory_id、原责任人、接管人、expected_resource_revision、状态、最后错误码、尝试次数、结果事件ID、created/updated/completed时间。

唯一键建议包含 `(change_request_id, adapter_key, resource_type, resource_id, responsibility_kind)`。一张单据有多种责任时必须区分，不能只按单据ID去重。

### 9.6 新增：可靠通知/交接发件箱 `IamOutbox`

仅在未找到满足条件的现有outbox时新增。最小字段：事件ID、类型、aggregate_id、payload、幂等键、状态、attempts、next_attempt_at、claimed_until、错误摘要。

它用于通知、交接、可观测性投影，不承担权限过期的安全边界。复用已有 `SystemNotification` 作为用户通知载体，避免两套铃铛消息。

### 9.7 是否新增岗位字典

本轮不把完整HR岗位字典作为必需前置。正式职位可以由管理员确认文字，并关联权限包；常用岗位方案可保存为命名模板。以后需要工号体系、职级、汇报线时再扩展，不因数据库模型好看而扩大本任务。

### 9.8 不变量与索引

- 每人在任一时点最多一段有效主职；同一用户任职编辑先锁该用户的identity版本行，再验证所有相关时间区间。
- 普通唯一索引不能阻止时间区间重叠。PostgreSQL可评估排斥约束；无论是否使用扩展，都必须有用户锁下的重叠校验与真实并发测试。
- SQLite不能假装支持PostgreSQL行锁；使用测试数据库的写事务串行化并执行同一重叠校验。
- 任职和关联授权均要求 `valid_until > valid_from`；`null` 与空字符串旧值按明确兼容转换处理。
- 下游授权时长不超过来源任职/代理来源/转授权限上限。
- 唯一业务键：actor + operation_kind + idempotency_key；相同键不同正文返回409。
- 索引覆盖 user_id、org_unit_id、时间区间、request_type/state、source_request_id、assignment_id。
- 不把“当前active”为条件但与时间变化有关的局部唯一索引当成完整主职约束。
- 不级联删除历史任职、授权事件、工作交接证据。

## 10. 时间模型与预约调动：后端时钟权威

### 10.1 统一语义

新接口使用含偏移的ISO8601；服务端标准化为UTC存储/比较，前端按 **Asia/Shanghai** 展示。既有字符串时间按照项目 `core/time.py` 的实际历史语义做适配，不全库猜测转换时区。

本轮预约范围明确限定为正式任职、兼职/支援和有时效的授权变化。冻结、离职、复职按立即办理交付；服务端拒绝这三类请求中的未来effective_at，前端不展示假预约按钮。以后需要“预约离职”时，必须增加认证前的账号生命周期时间线判定，不能只定时修改AuthUser.status；该增强不属于本轮已承诺的预约能力。

使用半开区间 `[valid_from, valid_until)`。例如“支援到10月7日结束”落为北京时间10月8日00:00的排他结束点，确认页同时显示自然语言和完整时间。

### 10.2 明确选择：时间生效不依赖后台轮询

V2预约采用**审批时一次性写入已批准的任职时间线及关联授权时间线**：旧任职在T结束，新任职在T开始。请求时根据服务器时间解析正式任职、权限和主页归属。

因此后台worker停止，也不能延长原岗位权限或使已经到期的临时授权继续有效；用户不需要退出重登才能完成时间边界切换。

为做到这一点，必须同时做到：

1. 任职与关联绑定、role_version、旧任职结束时间在同一事务提交。
2. 新增唯一权威解析器 `resolve_identity_at(db, user_id, at)`；认证、用户列表、目录、管理范围、业务身份检查都使用它或等价SQL查询。
3. `EmployeeProfile.primary_*` 只是兼容投影；不能让报价审核从旧主部门取值，而 `can()` 已按新任职允许。
4. 预约状态根据时间线推导。worker可以物化列表状态和发送通知，但不能决定授权是否有效。
5. `/auth/me` 返回 `server_now`、`next_transition_at`、`effective_context_key`；授权数据库版本没有在时间边界改变时，前端仍能识别当前有效身份变化。

**若这些调用链尚未改完，只开放立即变更，预约入口保持明确不可用。不能用一个cron更新主厂区就宣称预约功能完成。**

### 10.3 需要逐一适配的主组织消费者

只读检索已发现这些入口：

- `services/auth.py`、`services/iam.py`、`services/system.py`。
- `services/directory.py` 的主组织关联、列表过滤与汇总。
- `services/internal_quote.py` 的发起部门、销售审核资格和候选列表。
- `services/customer_price_settings.py` 的部门资格。
- `services/business_authz.py` 的本厂语义。
- `services/molding_sample.py` 中使用主厂区作为候选的逻辑。
- 前端 `stores/auth.ts`、应用厂区上下文、路由恢复、用户展示。

修改要点不是“把所有 primary_department 判定删掉”，而是对已迁移账号依据**当前有效、目标厂区匹配的正式任职**判断业务资格；对未迁移账号保留既有规则。没有正式销售任职的单纯权限补充，依然不构成销售审核身份。

### 10.4 时间线取消、改期、离职

- 生效前取消：锁定用户与计划，检查时间线revision；只撤销该计划新增的未来段，并恢复该计划确实改动的旧结束时间。
- 原结束时间已经被后来变更改动：返回冲突，重新规划；不能机械恢复历史快照覆盖后来决定。
- 已生效计划：只能新建反向变更；历史保留，不倒改生效时间。
- 离职：终止当前及未来内部任职/allow，撤销会话，取消或作废未生效计划；增加employment_epoch。复职不能使旧epoch授权复活。
- 权限包版本在计划批准前变动：旧预览失效。计划批准后使用已批准版本；需要变更时发起新的计划修订。
- 全局禁用权限/组织停用/账号冻结属于硬限制，仍可使已批准计划不可操作，并必须明确告警。

### 10.5 预约交接不是时间线判定的替代品

权限与正式身份按时间线生效；业务责任转交可能需要另一个真实业务动作。批准预约前确认交接方案，能提前转交的先办理，不能提前转交的登记待处理项。

到期后未完成交接的责任进入“待接管”，旧人员不能因仍写在assignee字段就继续操作；符合条件的新负责人办理正式接管后才接续。worker延迟必须显示，不能伪造任务实际执行时间，也不能把未交接的单据标记为完成。

## 11. 管理员授权边界

保留已有 `system:user_manage`、`system:access_manage`、`system:permission_catalog_read`、`system:audit_read` 等真实权限码。新增能力需在 `permission_codes.py` 中明确登记，并同步后端、前端、目录、种子和测试，不能只写前端字符串。

建议补充的能力（**新提案，非现有权限**）：

| 能力 | 建议码 | 说明 |
|---|---|---|
| 查看人员资料 | `system:user_read` | 敏感管理视图，不等于组织通讯录 |
| 更正正式基础资料 | `system:user_profile_manage` | 不可独立授予业务权限 |
| 办理正式任职 | `system:assignment_manage` | 涉及授权变化时仍需对应access_manage与转授范围 |
| 冻结/离职/恢复 | `system:user_lifecycle_manage` | 高影响操作；恢复不自动提权 |
| 办理职责接管 | `system:handover_manage` | 还需相应业务模块的可操作范围与接管规则 |
| 管理组织目录 | `system:organization_manage` | 不自动取得厂区业务操作权 |

旧user_manage权限如何映射新细分权限必须提供迁移影响表，不能让所有旧管理员意外失权，也不能把只读用户自动升为管理者。

对地方管理者存储明确的“可管组织 + 可管部门 + 可授角色/权限上限”。V2授权必须在该上限内；不要仅检查他在目标人身上有一个可管理binding，就允许修改此人其余厂区权限。

跨厂调动需要覆盖被撤销来源、目标组织和新增授权实际范围。只有A厂管理权的人不能直接决定B厂岗位；向有完整权限的管理员提交请求。

最后管理员约束覆盖：账号状态、明确deny、角色撤销、任职/独立管理员有效期、未来计划。执行涉及管理员存续的事务时锁定统一管理不变量行，再检查完整变化结果；两个并发请求不能分别看到“还有另一个管理员”后同时退出。

### 12.3 预览响应

至少返回：

```text
preview_token / expires_at
request_revision / identity_version / authorization_version
dependency_versions（角色版本、组织revision、关联来源等）
before_identity / after_identity
permission_diffs（按权限+厂区+部门，不只权限名称）
retained_sources / ended_sources / unresolved_sources
homepage_change
handover_summary（含未覆盖模块和重新检查时间）
requires_approval / reviewer_scope_requirements
blocking_issues / warnings / allowed_actions
server_now / effective_at / preview_fingerprint
```

预览只模拟，不发设备命令、不改权限、不真的转交任务。可以保存预览记录，但不得触发业务状态变更。

同一权限旧allow来源结束，但另一个独立来源仍允许时，摘要应显示“来源变化、操作能力保留”，不能把角色移除数直接当成用户失去的权限数。

### 12.4 提交与返回

提交正文保持简短：`preview_token`、`confirm_high_risk`、`expected_request_revision`。使用`Idempotency-Key`请求头或等价严格契约，不靠前端按钮disabled去重。

返回：稳定变更单ID、`applied/scheduled/pending_approval`、当前身份/授权版本、`effective_at`、`handover_status`、可执行动作。

网络超时后使用同一幂等键查询/重试；若已经成功，返回原提交结果，不能因为token已消费就误报一次新失败，更不能再创建第二次调动。

### 12.5 错误码与可恢复行为

| HTTP | 业务码示例 | 前端处理 |
|---|---|---|
| 400/422 | INVALID_ORG / INVALID_TIME_RANGE / INVALID_CHANGE | 字段级说明，保留草稿 |
| 401 | SESSION_REVOKED / ACCOUNT_UNAVAILABLE | 清理会话，进入登录/账号状态提示 |
| 403 | OUTSIDE_MANAGEABLE_SCOPE / GRANT_NOT_DELEGABLE | 不重试提权，提供申请/联系正确管理者入口 |
| 409 | IDENTITY_VERSION_CONFLICT / AUTHORIZATION_CHANGED | 刷新当前事实，再预览；不悄悄覆盖 |
| 409 | ROLE_VERSION_CHANGED / SOURCE_CHANGED | 更新依赖说明，再确认差异 |
| 409 | PRIMARY_ASSIGNMENT_OVERLAP | 展示冲突时间段和计划 |
| 409 | HANDOVER_ITEM_CHANGED | 单项重新评估，不重做已成功项目 |
| 409 | IDEMPOTENCY_PAYLOAD_MISMATCH | 阻止重复键不同内容 |
| 410 | PREVIEW_EXPIRED | 重新预览；不能直接复用旧摘要 |
| 503 | RETRYABLE_STORAGE_FAILURE | 保留草稿/幂等键，明确结果待确认 |

采用结构化错误，不暴露SQL、真实连接串、其他厂区敏感人员信息。后台详细错误以事件ID关联内部日志。

## 13. 一致性事务与并发

### 13.1 提交事务边界

```text
开始短事务
→ 校验幂等结果 / 锁定相关版本与请求
→ 重新读取操作者当前身份、管理范围和转授上限
→ 校验预览内容、用户版本、权限包版本、组织版本、来源有效性
→ 校验主职区间、范围与管理员存续不变量
→ 重新核实需要原子处理的业务交接版本
→ 写入旧任职结束、新任职/时间线、绑定与例外处理
→ 写入当前兼容投影或预约投影安排
→ 递增身份版本、授权版本
→ 消费预览，更新变更单
→ 写入审计与outbox、必要交接项
提交
→ 返回稳定结果
→ 交易外处理通知及可重试交接任务
```

这里的“原子”针对本次事务管理的数据库事实，不声称可以把打印机、网络通知或多个外部系统变成一个数据库事务。

### 13.2 不嵌套调用自行commit的服务

当前 `commit_system_position`、部分授权拒绝日志函数、用户状态函数会自行 `db.commit()`。不能把这些现成入口直接套进新变更事务，造成前半段已提交而后半段失败。

抽取不提交事务的领域原语，由最外层应用服务统一commit/rollback。既有入口和新入口调用同一原语，权限检查异常不允许顺便提交前面尚未完成的变更。

### 13.3 锁、版本与重试

为全部IAM写路径制定统一锁顺序，例如管理员不变量行→角色版本相关行→按用户ID排序的身份/授权版本行→变更单/预览→业务对象。最终顺序需与现有role/user写路径一起统一，不能每个服务自己规定。

- 角色发布、账号冻结、任职修改、旧权限提交路径都必须遵守同一互斥协议。
- 在获得锁后重新读取数据库事实，避免ORM身份缓存中的旧actor/role/scope数据。
- 锁持有期间不请求外部设备、不发送通知、不跑全厂大型扫描。
- 死锁/瞬时数据库异常只做有上限的整事务重试；幂等键防止重复结果。
- 并发冲突对用户显式409，而不是last-write-wins。

SQLAlchemy的ORM版本计数并不自动保护所有批量SQL修改；直接UPDATE/DELETE必须带期望版本条件、检查影响行数并按同一事务协议执行。PostgreSQL行锁只在实际使用并保持事务时提供对应保障，不能用“ORM应该会处理”代替测试。参见文末官方资料。

### 13.4 “立即撤权”的准确承诺

撤权事务提交之后新建立授权上下文的请求必须按新规则拒绝；不能继续依赖旧前端按钮状态。对冻结/离职，旧会话永久撤销，恢复后必须重新登录。

已经在撤权提交前通过校验的在途业务请求，不能宣称都能被追回。对IAM管理、高风险业务提交、设备命令等关键路径，评估执行前的版本复核/共同锁/调度时再次鉴权；已提交记录、已发出的设备动作或已下载数据不能靠改权限逆转。

正式任职由过去合法审批产生，批准者后来调岗不自动让所有被批准员工失去任职。只有声明为“依赖代理来源”的临时授权，才随该来源结束而结束。

## 14. 冻结、离职与复职的闭环

### 14.1 冻结

冻结账号与撤销全部active会话同事务完成，递增授权/身份版本并记录原因。已有任职可保留历史与原期限，但冻结期间不可使用。

恢复冻结账号必须重新评估当前时间内的任职/计划和仍有效授权；未到期、仍合法的任职可以继续，已过期或被撤销的例外不恢复。原revoked Session不得改回active。

### 14.2 离职

离职与冻结不同：终止当下及未来任职allow、取消未生效计划、撤销管理员/独立allow等实际访问来源、撤销会话、记录未交接责任、标记employment_status=left并更新epoch。

所有用户deny和审计可以保留历史；它们不应因为离职被当作“必须恢复的授权”。供应商等兼具外部身份者默认一并停止账号；确需转为外部协作身份，走明确的身份转换审批，不默认让离职者保留访问。

### 14.3 复职

使用同一用户ID，建立新的就业epoch与新任职。管理员复核正式组织、岗位与权限包，再允许登录。

旧“active/suspended”接口必须识别left状态：不能一个PATCH active就跳过复职审批。旧账号恢复不自动带回超管、过期支援、旧supplier allow或已撤销个人授权。

保留既有找回密码流程，不把复职自动实现为重置密码、下发临时口令或导出密码。

## 15. 前端设计：人员与权限中心

### 15.1 信息架构

复用并升级现有 `/system/users` 全页工作区，不占用普通员工的 `/people` 通讯录。保留原深链接并适配，不强迫所有业务入口重写。

建议一级导航四项：**人员、变更办理、权限方案、记录**。组织目录维护放在明确有权的管理入口中，不把八九个低频管理页堆成导航栏。

- 人员：日常查人、审核注册、看主职/兼任、发起调动。
- 变更办理：我的待审、预约生效、待交接、异常/冲突。
- 权限方案：内置权限包、自定义角色、版本影响、例外授权工具。
- 记录：人员时间线、变更单、权限差异、业务交接与审计查询。

现有 `/system/iam/requests`、`/system/iam/audit` 不再重定向到角色页，要有真实内容。`/system/users/:userId/access` 保持可访问，转到该人的“授权”视图，保留供应商等专门授权区。

### 15.2 桌面主布局

大屏可以左220px组织导航 + 中间弹性列表 + 右360–420px详情；空间不足时右侧转为覆盖式抽屉，不能硬挤列表。1280px优先两栏或列表+详情抽屉；手机组织筛选为弹层、人员变为卡片、办理向导单列。

展示“主职 + 兼任数量”，点击展开真实来源。不要把多任职压成无法读懂的逗号字符串。真实账号状态与在线presence分开，不把离线当停用。

所有统计尊重当前管理员可见范围；不允许通过总数泄露不在其范围内的人员规模或未公开岗位信息。

### 15.3 人员详情结构

页头：头像、姓名、账号状态、正式主组织、主职、兼任摘要；主动作“办理变更”，次动作“查看权限”。

四个上下文页签：正式资料、任职与授权、工作交接、变更记录。

任职卡包含正式组织/部门、正式职位、主职/兼任标签、起止时间、权限包、作用厂区、来源变更单。用户申报职位放在“注册申报”折叠区，不抢占正式身份主展示。

当前身份变化、未来计划和历史记录视觉区分。未来计划不能提前显示为已入职；已到期任务不等待worker才显示失效。

### 15.4 变更影响对照，不是密集勾选表

```text

待交接：X项 / 未覆盖模块：Y个

```

数量必须来自后端真实diff；示意UI不能写死“新增12、撤销8”。风险项按真实后果解释，例如“将获得其他厂区导出权限”，不只显示技术性“high”。

### 15.5 权限可解释视图

选择“用户 + 目标厂区 + 操作”，显示：

```text
是否允许：不允许
原因：这项授权来自临时支援任职，已于10月8日00:00到期
不是原因：账号没有登录 / 按钮没加载

```

支持查看指定时间的**已记录授权事实**；不能声称重放了没有保存快照的历史业务状态。对已记录的role_version、任职和deny可解释；若业务对象历史状态不足，明确“业务条件无法完整回放”。

只解释权限，不提供真正的“冒充该用户登录”，不生成可写模拟Session。

### 15.6 视觉与动效验收

保持现有白色/浅灰蓝/深青绿色企业风格，使用`DESIGN.md`和全局token。模块样式限定 `.iam-workspace` 等根命名空间；不改全站按钮、背景、登录、打印风格。

- 进页：标题、筛选、内容分组淡入，240–320ms，位移4–6px；不逐条动画数百用户。
- 一级导航：真实选中项驱动的滑动胶囊，180–220ms；请求失败不能假装已切换保存结果。
- 抽屉：240–260ms，`cubic-bezier(0.16, 1, 0.3, 1)`；关闭恢复焦点。
- 卡片/按钮：120–160ms，细边框、轻阴影和不超过2px位移；primary按钮可以局部微渐变，不做持续扫光。
- 预览差异：新增/终止/保留同时使用文字、图标与颜色，不靠红绿区分。
- 请求Loading保持按钮宽度，进度和计数只显示实际状态，不添加假等待和虚构百分比。
- 轮询刷新不重播入场动画，不把用户滚动位置跳回顶部。
- 支持 `prefers-reduced-motion`、键盘导航、焦点锁与恢复；复杂表单关闭有未保存提醒。
- 空数据、无搜索结果、无权限、加载失败、草稿冲突、过期预览分别设计，不能都是“暂无数据”。

建议组件职责：`IamWorkspaceShell`、`OrganizationScopeTree`、`PeopleTable`、`PersonInspector`、`AssignmentCard`、`IdentityChangeWizard`、`AccessImpactPanel`、`HandoverBoard`、`EffectiveAccessExplorer`、`IdentityTimeline`。

复用现有Iam组件内已正确的权限数据和可访问性处理，但不要把旧的“整包清理”动作放进新组件。所有纯图标操作使用项目Lucide图标并有可访问名称。

## 16. 登录会话、页面缓存与厂区同步

现有每请求从数据库获取权限的后端机制是优势，应保留。新增前端更新机制用于一致体验，不代替后端控制。

### 16.1 会话响应扩展

建议 `/api/auth/me` 增加：`identity_version`、`primary_assignment`、`active_assignments_summary`、`server_now`、`next_transition_at`、`effective_context_key`。原字段保持兼容。

`authorization_version` 表示持久化授权修改次数；时间到了但数据库未写入时，用`effective_context_key`与下一边界驱动刷新，不能要求所有过期事件都必须先有revision+1。

### 16.2 更新策略

- 管理员完成本人变更后刷新当前session；修改他人则发送可重试身份变更通知。
- 复用现有focus/visibility逻辑，并新增仅登录、在线、页面可见时的低频同步。默认可采用30–60秒作为产品预算，实施时测量请求量。
- 在下一任职/授权时间边界触发一次刷新；计算基于服务端时间偏差，不信任客户端手动改钟。
- 多标签页只广播“需刷新”信号，不广播Cookie、完整人员资料或作为可信授权数据的权限列表。
- 现有`sessionVersion`并发保护保留；旧响应不得覆盖后来登录/退出后的账号快照。
- 长连接消息、下载、异步任务结果返回也要保留各模块既有权限检查；不用一次连接鉴权替代永久授权。

### 16.3 厂区变化与草稿

正式主职厂区变化后，默认工作上下文更新；仍有权的业务深链接可以保留目标厂区，但必须显示清楚。无权旧页不能继续提交，展示“任职已变化”的上下文提示并清理旧授权下缓存的数据。

不要让未提交的A厂表单因为厂区自动变B而直接提交到B厂。表单固定记录创建时的资源厂区；权限变化后重新验证或转为只读。敏感草稿不自动持久化到localStorage，也不因为提醒而强制丢弃仍可合法使用的输入。

保持当前约定：厂区选择在内存中管理，不把它新增存入浏览器storage；普通同账号刷新不重置用户手动选择；集团归属进入neutral group，不从第一个角色推导厂区。

### 16.4 敏感管理页与普通浏览页区分

只对人员管理、授权变更、管理审计等敏感路由增加/核实严格权限控制；保留业务页既有“已登录可进入页面”策略。后端无数据权限时显示真实拒绝，不能为了页面能进而放开读取。

普通 `/api/directory` 与 `/people` 继续保持低敏只读契约，不能直接改成复用管理员接口返回姓名以外的账号、电话、邮箱、权限详情和会话记录。

## 17. 旧接口与系统初始化的收敛

这是必须交付的后端工作，不因新UI不再调用旧接口就省略。

### 17.1 旧“内置职位替换”接口

对V2账号，不再允许执行“清理所有其他角色/一般override”算法。

可以选择兼容适配到同厂、同任职的完整预览流程，或返回明确409 `IDENTITY_CHANGE_REQUIRED`。不能把一次缺少厂区、任职、例外处理策略的旧请求，猜测成全量换岗。

历史整改需要保留时，使用独立受控维护入口，并详细说明将删除哪些有效/未来来源；普通日常管理不可进入隐式全清理路径。

### 17.2 旧角色/override/状态写入

- 直接修改assignment关联绑定，必须通过同一服务更新任职来源约束与版本。
- 独立例外仍可通过原preview/commit管理，但要求合法source和生命周期策略。
- 对left账号不能通过旧status端点直接恢复；冻结端点应复用会话撤销原语。
- 旧注册审核与新任职创建在一个事务，不允许激活账号后再异步补主职。
- 旧申请列表不能重复处理新identity-change；审核权限在真正approve时重查。

### 17.3 启动种子与内置模板reconcile

逐项审阅 `seed_iam_sidecars`、`seed_auth_defaults`、各一次性默认授权补齐和 `system_position_reconcile.py`。

必须保证：服务重启、模板reconcile、迁移重跑不会恢复已撤销的任职/权限，不会把未来有效期清空，不会新增另一条绕过assignment的新legacy binding。

代码内置模板更新与已批准V2绑定的升级建立显式版本桥接；不能为了让测试变绿而让snapshot和实时权限表同时授权取并集。

## 18. 线上存量迁移与回退

### 18.1 原则

扩展式迁移优先。保留稳定用户ID、厂区ID、角色ID、会话体系、历史单据和审计引用。先有读兼容，再有新增写入，最后停用旧写路径。

`identity_mode` 控制用户任职模型，`AUTHZ_MODE` 控制现有授权执行模式，两者不是同一个开关。某用户切到V2后，只能有一个有效权限来源体系，不能V2拒绝后再OR旧权限兜底。

### 18.2 迁移前检查报告

Codex需实现只读预检工具，输出汇总与需要人工核实的具体条目；真实人员明细保存在受控环境，不写入公开开发日志。

检查：

- 当前实际AUTHZ_MODE、AUTHZ_WRITES_ENABLED和数据库迁移版本。
- 所有正式档案、有效/未来角色绑定、allow/deny、来源、会话状态。
- 缺profile、未知组织、部门别名、多个主职候选、排序第一职位与真实岗位不一致。
- wildcard超管、总经理、跨厂仓库经理、供应商独立授权、外部与内部复合身份。
- 活跃/过期/未来授权元数据、缺失sidecar、重复来源、无效permission code。
- 旧的待批预览/请求与未来计划、注册未审核用户。
- 与主部门/主厂区有关的业务资格、角色候选和责任归属。

来源归属不足时标记待核实，不根据中文职位、用户名或第一个role猜测。已被历史清理删除且没有完整证据的权限不能“凭记忆恢复”。

### 18.3 五步迁移流程

**步骤A：建立可恢复基线。** 经生产操作另行授权后备份数据库并验证恢复；记录所有相关表的数量、主外键关系、用户版本和授权快照。备份完成不等于恢复演练通过。

**步骤B：部署兼容结构。** Alembic增加表/可空列/索引；新特性默认不改现有授权判定。禁止把主组织缺失者直接填到A厂。

**步骤C：构造任职映射并比较。** 对来源明确者构造主职和权限关联；其他独立权限保留。对六厂及特殊global范围、相关部门、真实权限集合，比较变更前后允许/拒绝结果；结合业务代表对象测试，不能把有限布尔矩阵声称为所有业务对象的数学证明。

**步骤D：处理歧义与模式切换。** 管理员核实来源；逐用户迁移时锁版本并重读，避免预检期间新增注册/授权造成过期覆盖。只有经验证的授权保持型迁移可自动通过。真实权限整改应另开变更单。

**步骤E：受控上线。** 新注册审核接入任职流程，迁移用户切到V2权威读取，关闭对应旧写路径。持续检查拒绝异常、未覆盖交接和身份投影差异。

### 18.4 legacy/shadow/enforce衔接

不能直接把生产legacy改成enforce以让新UI按钮可用。

先比较现有业务授权差异，保留现有shadow观测行为，修复或批准差异后才切换enforce。通用V2任职/授权写入要求enforce；若条件未满足，页面显示迁移状态与只读预检，不静默绕过 `_require_writes_enabled()`。

供应商三项权限原有窄例外继续按现有服务执行，但不能作为“其他所有权限也能在legacy下写”的理由。

### 18.5 回退的正确边界

上线前准备一个**已支持V2读取、会话撤销和时间线语义的兼容回退版本**。关闭V2新增写入与新UI不应重新授予旧权。

已发生调动、离职或撤权之后，不能退回不理解assignment/source/epoch的旧二进制，也不能退到legacy让旧授权重新生效。错误人员变更通过审计可见的新反向变更修复，而不是恢复整库旧快照覆盖随后发生的业务。

结构扩展的down迁移只允许在未有新结构业务写入或专门维护演练中执行；有真实V2数据后禁止“为回退自动DROP新表”。

### 18.6 迁移完成标准

已迁移账号的稳定ID与历史单据关联不变；所有活跃授权来源可解释；未分类历史来源数量为0或明确隔离在未切换账号；实际权限差异全部有管理员认可的变更依据；新旧接口不会分别写出冲突状态。

不能仅以“迁移脚本成功退出”作为迁移完成。

上线前由实际操作人员确认：授权模式、迁移版本、兼容回退版本、数据备份恢复结果、最后有效管理员、未分类用户清单、交接覆盖清单。

业务指标与错误指标建议包括：

- 变更提交成功/冲突/失败、待审数量、未分类授权数量。
- 已到期授权仍被允许的异常断言；身份解析与兼容投影不一致数量。
- 预约计划、未完成接管、未覆盖模块、outbox重试与延迟。
- 权限拒绝变化按模块/范围聚合，不在普通管理UI暴露其他用户敏感操作内容。
- 最后管理员存续与未来有效期风险。

性能目标须用测试样本与实际部署环境测量；本文件不提供虚构的当前QPS或用户规模。分页人员列表避免逐用户N+1构造全权限矩阵；摘要只取必要数据，选择单个用户时再计算详细授权解释。

批量预览需分批、可取消、可恢复；不能在一个大事务里锁住全公司用户并生成所有权限组合。

## 24. 默认决策与待生产确认事项

为保证Codex可以先开发，不以反复提问阻塞，本文给出默认策略：

| 项目 | 默认决策 | 真实上线前须确认 |
|---|---|---|
| 六厂ID | 沿用现有六个稳定ID | 不需重新命名 |
| 总务 | 保留management部门；另支持集团职能归属 | 哪些人实际属于集团总务，不自动迁移 |
| 任职模式 | 一主职、多兼任/临时 | 每人真实主组织与兼任事实 |
| 常规审批 | 有完整权限管理员直接确认 | 地方管理者的授权上限 |
| 跨厂调动 | 集团或覆盖完整范围管理者办理 | 是否需要额外人事联合确认 |
| 历史数据 | 不变厂区、不改历史创建/审批人 | 哪些未完成责任可以转交 |
| 个人deny | 原范围保留 | 只有明确审批才解除 |
| supplier例外 | 调岗保留，离职整体停止 | 外部身份转换需独立确认 |
| 预约生效 | 服务器时间解析任职与权限 | 所有主组织消费者适配完成 |
| 模板升级 | V2版本化影响预览 | 是否对某些低风险包允许受审计批量升级 |
| 未分类历史权 | 人工核实 | 不根据职位字符串推断 |
| 生产发布 | 本次不自动执行 | 用户另行授权上线与真实数据迁移 |

本文不声称能提前知道所有未来组织政策。扩展点集中在任职类型、明确权限包、范围、时间和模块交接适配器，而不是允许管理员写任意脚本/规则表达式。

## 26. 最终完成判据

管理员能在一个人的详情中清楚回答：**他现在属于哪里、实际担任哪些职位、每个厂能做什么、每项权限来自哪里、什么时候失效、换岗会影响哪些工作、过去是谁确认的。**

真实用户从华康A工程调到华兴仓库后，新组织和新授权一致，原任职权在正确时间停止；其他合法兼任不会被误删，历史业务证据不搬厂，未完成责任有接管入口。离职立即停止访问，复职重新确认，不靠删除重建账号解决问题。

只有这些流程在真实接口、数据库和浏览器中验证通过，才可以称为本次人员与权限模块开发闭环完成。
