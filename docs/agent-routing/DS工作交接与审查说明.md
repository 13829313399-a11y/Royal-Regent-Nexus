# 大肥鱼 DS 工作交接与 Codex 审查说明

适用项目：Royal Regent Nexus。交接对象：大肥鱼 DS。审查与验收负责人：Codex。业务需求和发布授权由用户决定。

DS 承接范围明确、影响有限的实现任务，Codex 根据实际代码差异、业务契约和验证证据审查。DS 的“已完成”表示可以送审，不等于已经验收或上线。每次只交接一个可以独立检查的任务。

本说明用于人工转交任务，不配置模型提供商，不开通权限，不自动发送项目资料或服务器凭据，也不授予 Git 提交、远程推送或生产部署权限。用户后续的明确指令优先。

## 1. 工作分工与任务范围

| 工作 | DS 的职责 | Codex 的职责 |
| --- | --- | --- |
| 明确的局部排版、文案、显示问题 | 阅读现有实现，完成最小修改和相关验证 | 核对需求、共享组件影响、实际显示和交互 |
| 已定位的局部缺陷 | 保留原业务语义，修复原因，提供复现和验证结果 | 检查根因、边界条件和回归风险 |
| 复杂或跨模块问题 | 先定位原因、列出涉及的代码和疑点，暂不扩大实现范围 | 判断方案与影响，必要时交由用户决定业务规则 |
| 库存、价格、月结、审批、权限、导入、数据库或部署 | 默认仅调查和提供方案；有明确专项任务时按专项边界执行 | 负责严格审查与验收，按用户授权安排执行 |

“简单”按业务影响判断，不按改了几行代码判断。例如，“按钮换个位置”通常是小任务；“修改按钮点击后直接通过供应商审批”即使只改一行，也属于流程变更。

适合直接交给 DS 的例子：按钮左右顺序、窄弹窗字段挤压、统一非业务性提示文案、共享组件中已明确的展示缺陷、修正文档引用。

需要先交给 Codex 判断的例子：更改实收入库公式、价格自动覆盖、减少月结校验、补单与退货状态、跨厂区查询、修改权限、重构正单与样板单的数据模型、历史数据整理和生产更新。DS 发现任务触及这些范围时，先交回定位结果；不需要为已明确授权的普通样式选择反复询问用户。

## 2. 开始前必须确认

1. 阅读根目录 [AGENTS.md](../../AGENTS.md)，再检索并完整阅读 [PROJECT_MEMORY.md](../../PROJECT_MEMORY.md) 中与任务有关的段落。记忆不清或与现状冲突时，先核对真实代码和最新用户要求。
2. 确认工作目录、当前分支、基准提交和已有未提交修改。不得覆盖他人改动，不得为了“清理环境”执行强制重置或清空工作区。
3. 阅读目标路由、组件、API 调用及相关测试。索引只用于定位；页面截图、菜单文字、模拟数据不能证明后端规则已经实现。
4. UI 任务还要读取 [DESIGN.md](../../DESIGN.md)、[前端工作流](../frontend/WORKFLOWS.md)、实际共享组件及样式。普通小修无需重新设计整页。
5. 写清本次预期结果、允许修改范围和验收动作。缺少会影响正确性的业务决定时才提出问题，其余按现有规则执行。

主应用是 Vue 3、TypeScript、Vite 和 Pinia；后端是 FastAPI、SQLAlchemy、Alembic。生产数据库为 PostgreSQL，本地数据库以当前配置为准。子项目要读取自己的依赖，不把主应用技术约定直接套过去。

同一份工作区不要让 DS 和 Codex 同时修改同一文件。DS 送审后应暂时停止修改待审内容；若继续修改，必须告知新增差异，由 Codex 对最终版本复核。需要隔离时由任务负责人安排独立工作区，不能直接覆盖另一份未提交成果。

## 3. 所有任务必须保留的边界

- 厂区必须明确且经过验证，不能默认退回其他厂区。前端隐藏按钮不能代替后端权限检查；不能为了测试方便放开认证或使用管理员身份掩盖普通账号问题。
- 单号、合同号、货号和物料编码按字符串处理，保留前导零。不能擅自转换金额币种、尺寸单位或数量单位，也不能把空值当成零。
- 保留原有请求版本、重复提交保护、权限复核和事务约束。请求结果未知时先核实或使用原请求重试，不能换新请求号再提交一次。
- 优先修改现有共享组件和已有流程。不要为了实现表面一致，复制整套页面、接口或账本。
- 历史订单、送货、入库、库存、结算、附件和审计证据必须保留。隐藏入口不等于删除历史数据；修复界面不能重建订单编号或替换历史关联。
- 不修改已经应用的历史迁移，不直接改真实数据库来制造通过结果，不通过删测试、跳过断言或修改预期掩盖缺陷。
- 不顺手升级依赖、格式化整个文件库、重做无关模块或修改运行时开关。确有必要的额外变更要说明原因和影响。
- 密码、令牌、Cookie、真实客户文件和生产数据不得写入交接说明、测试日志或提交内容。需要样例时使用脱敏数据，保留触发问题所需的结构。

## 4. 纸箱模块重点注意事项

以下是当前协作中最容易被误改的规则。详细契约以 [纸箱模块业务逻辑说明书](../business/纸箱模块业务逻辑说明书.md)、[月结与供应商对账方案](../business/纸箱月结与供应商对账方案.md)、项目记忆和实际实现共同核对；不能用本节概括替换具体接口约束。

### 4.1 三种订单复用界面，保留真实来源

内部端和供应商端的正单、样板单、杂单复用现有新建、复制、明细、采购单和更多操作的共享实现。样板单、杂单不要求重新填写来源、合同、客户、需求人或车间，不提供拆单合单；已有历史信息仍要保留。

界面复用不等于合并后台数据。样板单、杂单继续保留自己的真实来源、编号、版本和 API，不伪造正单、合同或采购下发记录。不同来源可以使用适配器处理资格和请求差异，不能再分别复制一整套界面。内部端功能一致也不意味着供应商获得内部创建或修改权限。

### 4.2 已完成订单和供应商确认

已完成样板单、杂单的补单、退货和可用的追加操作沿用真实来源及库存证据。补单不等于增加原单需求；退货不等于减单。不能为了显示菜单，直接移除状态、库存或权限限制。

“调整订单信息”的纸品资料更正需要供应商按当前流程确认；已发布需求的追加、减单、交期调整要保留新版本及供应商重新确认规则。按钮名称可以调整，审批和版本约束不能随之消失。

### 4.3 到货、拒收与实际入库

区分到货数量、破损、拒收、其他不可用和有效入库。整批拒收的有效入库应为零，不能因为显示了到货数量就说已经入库。修改标签或排版时必须保留后端字段含义，避免前后端各扣一次。

手工新收料、导入送货单验收和历史重录的数量契约存在差别，不能直接把一套计算覆盖所有入口。仓位分配对应实际有效入库；已有待核实或冲销后待更正的送货单必须继续处理原单，不能另建一张绕过它。

无单验收选择样板单或杂单时，不再强迫填写客户、需求人、车间、用途。真正属于正单的货物仍需按流程补建或关联；纸品不同不能随便关联。同一批货只能入库一次，不能仅凭信息看起来相似就自动合并。

### 4.4 供应商价格与月结

供应商送货单验收采用供应商原价；常规验收不再提供仓库价格核对选择器。空价不等于零，零价不自动等于免费；缺价可以按现有规则先收货，但不能因此跳过最终结算的价格核实。

手工入库后首次收到供应商原价，只有准确关联到同一已收批次时，才按现有流程采用供应商价并通知仓库。这里更新的是应付价格证据，不重复入库，也不直接覆盖原收料、仓位或库存估值。后续价格更正、已确认或锁定的月结必须走既有更正或重开流程，不能扩展成任何供应商价格都无条件覆盖。

月结页面可以简化展示，但缺价、未确认差异、有效数量、退货及版本确认等检查必须继续存在。“没有差异”应来自真实核对结果，不能通过隐藏异常或默认确认来实现。

## 5. DS 的实施和验证流程

先复现或确认问题，再说明修改位置，完成最小修改，检查差异，运行相关验证，最后按第 7 节格式送审。不要把未执行的检查写成通过，也不要用旧版本的测试结果证明新差异正确。

先读取当前 `package.json`。本仓库现有检查包括：

```powershell
npm run build
npm run test:unit -- <实际存在的相关测试路径>
npm run typecheck:test
git diff --check
```

尖括号内容是占位，必须替换后执行。前端代码变更按项目要求完成构建；测试改动涉及类型时执行测试类型检查。不要虚构 `lint` 脚本。后端修改使用当前可用 Python 环境运行对应测试，先确认测试库隔离，不能连接生产数据库运行测试。

UI 变更使用项目要求的 Chrome DevTools MCP 检查真实路由、账号权限、厂区、相关状态和实际视口，保存截图或明确记录未落盘情况。工具不可用时记录具体限制，继续独立检查，不自行换另一套浏览器工具。构建通过不能替代视觉和交互检查。

本地源码或运行配置更新后，按现有用户约定重启当前工作区的前后端并验证就绪；由启动器管理时同时处理文档 worker。先识别进程归属，不能误停其他工作区。`npm run dev:local` 会复用健康进程，本身不代表已经重启。当前生产状态和本地数据路径必须读实际配置与项目记忆，不能凭旧聊天记录推断。

只有文档或工作流说明修改时，检查内容、引用和差异即可，不运行无关应用构建。对于纯排版小修，不为凑数量新增复述实现的测试；应验证真正可能受影响的行为。

## 7. DS 必须提交的结果

```text
任务：
基准提交及当前工作区：
结果：待 Codex 审查

修改文件：逐个说明用途，不把他人已有改动算入本任务。
实现行为：用户操作前后发生什么变化。
实际代码：同一工作区提供可核对的差异；另一工作区提供基于明确版本的补丁。
验证结果：逐条列实际命令、退出结果、失败原因和未执行项。
UI 证据：路由、厂区、账号权限类型、状态、视口、截图实际路径。
业务影响：是否涉及 API、数据、权限、状态、库存、价格或历史兼容。
剩余问题：未解决项、环境限制和需要负责人决定的事项。
Git 与部署：如实说明是否执行；没有执行就写未执行。
```

口头描述或一张“成功”截图不能替代代码差异。代码有后续变动时要更新交付内容，不能继续引用旧的通过结论。

## 8. Codex 的审查和验收职责

Codex 先核对用户要求、基准版本和完整差异，再检查调用关系、共享组件影响及相关测试。重点检查是否另做一套页面、误改字段含义、放宽权限或状态限制、破坏厂区隔离、重复入库、覆盖历史价格或丢失既有数据。

审查要独立读取代码并执行必要验证，不能只转述 DS 的自检结果。发现问题时提供具体文件位置、触发条件、影响和修改要求。范围内的小问题可直接修复并重新验证；需要 DS 返工时由用户转交，未经授权不自动向外部服务发送代码或消息。

结论使用以下四种之一：

- **通过**：授权范围内的验收条件与必要检查均已满足，没有已知阻塞项。
- **需要修改**：存在明确缺陷，列出问题及修复后的验收条件。
- **待验证**：暂未发现阻塞缺陷，但缺少必要的环境、运行或界面证据，不能标记通过。
- **需要业务决定**：现有要求不足以决定正确行为，向用户提出具体问题及影响。

审查报告写清任务与版本、结论、主要发现、实际验证和剩余风险。通过只适用于被审查的最终代码，后续新增差异需要重新确认。审查通过不自动授权合并或上线；Git 操作和生产更新仍遵守用户明确授权及项目发布流程。

## 9. 用户如何使用

把本说明和第 6 节填好的任务交接单交给 DS。DS 完成后，把它的代码差异、交付报告和截图交给 Codex，并说明“按本说明审查”。如果双方使用同一工作区，提供任务范围和基准提交即可，由 Codex 读取实际差异。

本说明不能证明任何新改动已经上线。部署身份应以实际服务器 Git 版本、镜像、数据库版本和已验证发布记录共同确认；生产凭据继续由用户单独管理。
